# Using Lunport

Lunport is your SSH workspace for hosts, keys and Groups. Download the current Stable from [Releases](https://github.com/ysya/lunport/releases/latest).

## Your host library

A new installation opens a Records workspace without requiring an SSH config or an existing data directory. The first save creates the local library. Add a host with its hostname, username and port, or use **Import** to review entries from OpenSSH files. Import copies the selected data and preserves the sources.

Groups provide shared connection defaults and can contain other Groups. Host overrides remain explicit. Open **Hosts** in the sidebar, then use **All hosts**, **Groups** or **Tags** in the page to browse. The Groups page shows root Groups and Ungrouped hosts; open a Group to browse its children and hosts. The Tags page lets you search tags and open their hosts. Open the All hosts title menu to switch between **All hosts**, **Recent** and **Needs attention**. When hosts need attention, a small alert count in the page header opens that view directly. You can also find connections with **⌘K / Ctrl+K**. Use the **⋯** menu beside **New host** for **Import hosts** or **New group**. **Settings** opens from the upper-right toolbar or **⌘, / Ctrl+,** and provides search across the preferences available in your workspace.

Host and key details open over the right side of the workspace, keeping the catalog width and scroll position unchanged. Drag the detail divider to resize it on wide windows. **Escape** or **Close details** returns to the selected item; narrow windows show details across the workspace without rebuilding the collection.

### Files on a host

Select a ready host and choose **Files** in its details. Lunport uses the saved SSH route and authentication to browse remote folders through SFTP. Choose **Upload…** or drop one local file into the Files window to copy it with SCP to the current remote folder. If a regular file with that name already exists, Lunport asks before replacing it. Select **Download…** beside a remote file to choose a local destination. Downloads never replace an existing local file. The progress area shows transferred bytes and lets you cancel; a canceled upload can leave a partial remote file.

The Files window transfers one regular file at a time. Links and other special files are shown but cannot be downloaded from this window. The remote server must support SFTP for browsing and its SCP program for transfers. The single-file limit is under **Settings → AI access → File transfers**; it also applies to transfers started from Files. This human-initiated window uses normal connection prompts and does not need AI access to be enabled.

**Settings** opens as a full-window page with category navigation and search. Use **Back** or **Escape** to return to your workspace; host selection, scroll position and terminal sessions are preserved. **⌘F / Ctrl+F** focuses settings search while the page is open. An unapplied SSH config path draft still requires confirmation before leaving.

In **Hosts**, the Browse pane keeps All hosts, Recent, Needs attention, nested Groups, Ungrouped, and Tags in one place. Search the Browse pane to find a Group or Tag, or search the selected Host list separately. Selecting a Group shows only Hosts directly in it; expand the Group to see its subgroups, and use **New subgroup** to add one. The breadcrumb shows the full Group path and lets you return to any ancestor. Host cards in cross-group lists show their full Group path. On a narrow window, use **Browse** to open the collection pane.

Drag a Group within its current level to reorder it. With the Group focused, use **Alt+↑ / Alt+↓** (Option on macOS) for keyboard ordering. **Groups → ⋯ → Sort groups by name** restores name sorting. Sorting preserves nesting and connection defaults, and newly added Groups follow manually ordered peers. With an account, order syncs to your computers; concurrent offline reorders converge through the existing sync rules. Older 1.2.0 clients continue using name sorting while retaining the additional encrypted metadata.

## Appearance and color themes

Open **Settings → Appearance → Color theme** to choose Lunport, Nord, Dracula, Catppuccin, Tokyo Night or Solarized. The miniature previews follow the selected **System / Light / Dark** mode. Selections apply immediately and are remembered on this installation; the original Lunport palette remains the default. Settings search also finds themes by name.

Each preset covers the workspace, sidebar, cards, dialogs and status colors. Dracula uses Alucard in light mode; Catppuccin uses Latte/Mocha, and Tokyo Night uses Day/Night. Surface roles and status colors are adapted for interface text contrast. **Theme credits** includes palette sources and licenses. External terminals such as iTerm2 and Terminal keep their own color preferences.

## Server identities and connection checks

Open **Settings → Connections → Known hosts**, or choose **Manage identity…** in a host's connection details. **Lunport identities** shows the saved address, key type, fingerprint, verification time and originating device. You can copy a fingerprint, verify it again, or forget it after reviewing the confirmation. Forgetting a shared host's identity syncs to your other computers; its host settings and login keys remain saved. The next connection requires a new trust decision.

The **OpenSSH known_hosts** tab manages this computer's `~/.ssh/known_hosts`. Search by host, fingerprint or key type; hashed names remain hidden. Removing an entry first saves a backup and checks that the complete displayed line is still current. Changes in this tab apply to OpenSSH's local file. Lunport's SSH client uses the separate identities shown in the first tab.

In a host's connection details, **Check port** performs a manual TCP reachability check with a three-second limit and displays the result, connection time and check time. A reachable port confirms TCP connectivity; server identity and login are verified separately. Timeout, refused connection and name-resolution errors describe that check rather than declaring a host offline. For jump-host routes, use **Verify fingerprint** to check through the configured route; that flow may request jump-host credentials. A host that connects through Google Cloud IAP has **Check through IAP** in its place, described under [Google Cloud IAP and OS Login](#google-cloud-iap-and-os-login).

## SSH tunnels

Open **Tunnels** in the Records workspace and choose **New tunnel**. Select a saved SSH host and a forwarding type:

- **Local:** listen on this computer and reach a destination from the SSH host, such as `127.0.0.1:15432 → db.internal:5432`.
- **Remote:** listen on the SSH host and reach a destination from this computer. The SSH server must allow remote forwarding; its `GatewayPorts` policy controls non-loopback exposure.
- **SOCKS5:** point a browser or tool at the local listening address. TCP CONNECT is supported, including destination name resolution through the SSH host. UDP and SOCKS authentication are not supported.

Listening addresses are IPv4 or IPv6 addresses. The default `127.0.0.1` is loopback; choose port **0** to allocate an available listening port. The actual port appears after starting. Each tunnel uses the host's existing keys, passwords, server fingerprint checks and jump hosts, without opening a shell.

Rules sync as encrypted account metadata. **Running state stays on each device:** receiving a rule never starts it, and changes elsewhere do not reconfigure an existing connection. Stop and start to apply an updated rule. A rule deleted elsewhere stays visible until its local connection is stopped. On leaving sync, rules for preserved hosts become local rules.

Tunnels keep running while switching pages, closing terminal tabs or closing the window. Quitting Lunport, reloading it or installing an update ends them. Reconnection is manual. Up to 16 tunnels can run on one device, each with up to 64 simultaneous TCP connections; up to 256 definitions can be saved.

An AI client can also manage the tunnels of hosts it may use (see [AI access through MCP](#ai-access-through-mcp)). A tunnel it started says **Started by an AI client** while it runs, and stops by itself when you turn off the client's access to its host.

## Cloud SQL databases

A saved database is a Cloud SQL for PostgreSQL instance that Lunport signs in to for your other apps, such as `psql` or DataGrip. Lunport offers it on a port of this computer, signs in to Cloud SQL as your Google account, asks for a Privileged Access Manager grant first when the database needs one, and keeps a prod database read-only until you unlock writes, all without gcloud or the Cloud SQL Auth Proxy running. This release supports PostgreSQL with IAM database sign-in only, over the instance's public IP or over its private IP through a host saved in your library (see **Route** below): the instance needs IAM sign-in turned on, Lunport signs in as your Google account, whose email is the database user, and it never sends a database password to Cloud SQL. On Google's side, your Google account must be an IAM database user of the instance, which needs IAM database authentication on (its `cloudsql.iam_authentication` flag), and the account needs the Cloud SQL Instance User role (`roles/cloudsql.instanceUser`) to sign in and the Cloud SQL Client role (`roles/cloudsql.client`) to connect.

Open **Cloud SQL** under **Connections** in the Records workspace, beside **Tunnels**, and choose **New database**. Choose an instance first; its connection, local access and advanced settings appear after you select or enter one:

- **Instance:** **Pick from Google Cloud** lists the PostgreSQL instances of a project for the chosen **Google account** (gcloud's active account unless you choose another); enter the project id and pick an instance. An instance with IAM sign-in off is listed but cannot be picked, and the list says why: "IAM sign-in is off on this instance." Each row names the addresses the instance has (**Public IP**, **Public IP and private IP**, **Private IP only** or **No IP address**) and, for an instance with no public IP, the host it will go through, as **Route** below describes. When Google cannot list the instances, the dialog shows its sentence instead. **Enter a connection name** takes `project:region:instance` as the Google Cloud console shows it, such as `acme-dev-654321:asia-east1:orders-pg`.
- **Route:** how Lunport reaches the instance: **Public IP**, or **Through a host** saved in your library, which reaches the instance's private IP. Lunport connects to that host exactly as a connection to it does, with its Google Cloud IAP route or jump hosts, its grant, its saved server identity and your keys, and the path it opens ends at the instance's private IP on port 3307, which the host must be able to reach; the host's SSH server must allow TCP forwarding. Picking an instance without a public IP chooses the host for you when exactly one host in your library has its own Google Cloud IAP route in the instance's project, and the instance's row then says "Private IP only · via web-1". With several such hosts the row says "Private IP only · Choose a host", and you choose one in **Route**, which shows up to six suggested hosts and the current selection, then lets you search all hosts by name, address or full Group path, including hosts outside the project; with none it says "Private IP only · Needs a jump host", and **Route** offers **New IAP host**, which closes the dialog (after asking, when you have unsaved changes) and opens the host editor with Google Cloud IAP already chosen. **Save database** saves nothing and says "Choose a host to connect through." while a database over its private IP has no host, and picking an instance that has a public IP sets the route back to **Public IP**. The route is saved with the database, so it syncs with it. When the host is no longer in your library, the route stays: the row, the editor and the route line say **Host unavailable**, and Start fails with "Orders connects through a host that is no longer in your library. Choose another host in its settings." until you choose another.
- **Name:** what the list calls the database, up to 128 characters. It follows the instance you pick or type until you type a name of your own.
- **Default database:** the database on the instance that the connection URL opens, up to 63 characters: `postgres` until you change it, and again whenever you pick another instance.
- **Environment:** **Dev**, **Staging** or **Prod**, shown as a badge on the database. Only **Prod** changes how Lunport treats a connection, as described below. A new database has none chosen, and **Save database** waits, with "Choose Dev, Staging or Prod.", until you choose one; a saved database keeps its own.
- **Let other apps connect:** on by default for a new database, with a suggested **Port on 127.0.0.1**: the first free port from 6543 up that no other saved database holds (any port from 1024 to 65535 is accepted). Without it the database has no local port and cannot be started.
- **Advanced access → Requires a PAM grant:** a connection needs an active grant on one of the **Entitlements** (for example `prod-operate`) in the database's project, in the `global` location.

**Start** first listens on the local port and then opens the whole way to the instance, and the row reads Starting until the way is open; **Stop** closes the port together with every connection through it and the session to the host a database is reached through. While connections are open, **Stop** asks first, for example "Stop Orders? 2 active connections will close."; with none open it stops at once. A row shows the **Local address** (`127.0.0.1:6543`, or **Not shared**), the status (Stopped, Starting, Running, Stopping or Failed, with **Retry** after a failure) and, while it runs, the number of active connections. A database reached through a host says "via web-1" after its instance. While it starts, the **Status** column adds the step Start is at: "Requesting grant…" for the database's own grant, when it requires one; "Connecting through web-1…" while the SSH session to the host opens; and "Getting the Cloud SQL certificate…". The host's own grant is asked for during the connecting step, in Lunport's **Request a grant** window, and the row reads "Requesting grant…" while that window is open. When the last step is done the row reads Running; a step that cannot be done ends the start in Failed, with that step's sentence on the row. A running database cannot be edited or deleted; stop it first. It keeps running while you switch pages or close the window. Quitting Lunport or installing an update stops it, and nothing starts by itself.

A database reached through a host keeps one SSH session to that host while it runs, and all its connections share it. Lunport forwards a port that the system picks on 127.0.0.1 through that session to the instance's private IP on port 3307, and your apps still connect to the database's local port. The connection to Cloud SQL is TLS with IAM sign-in, as for a database on its public IP, and Cloud SQL's server certificate is checked against the instance's own name, not the address Lunport dials. When the session drops, the connections open through it end, and the next connection an app makes opens it again, asking for a grant again when one is needed. Nothing listens beyond 127.0.0.1.

Select a database by its name or the arrow in its row to open its details beside the list, or below it in a narrow window. Edit and Delete are in the selected details; a database without a local port can still be selected. The local connection card begins with the **Route**: the way from Lunport to the instance, part by part, each part colored by how far Start got, such as "Lunport → IAP → web-1 → 198.51.100.10:3307 → Cloud SQL (TLS, IAM)". The IAP part is there when the connection to the host begins with a Google Cloud IAP route, and the instance's address replaces "Private IP" once Start has fetched it. A database on its public IP reads "Lunport → Public IP → Cloud SQL (TLS, IAM)" until then, and a host that is no longer in your library reads "Host unavailable". **Copy URL** copies the connection URL, `postgresql://{user}@127.0.0.1:{port}/{database}`, where the user is the database user Lunport signs in as (the email of the database's Google account, or of gcloud's active account when it names none) and the database is the **Default database**, both URL-encoded. **Copy JDBC URL** copies the same address for JDBC apps such as DataGrip, `jdbc:postgresql://127.0.0.1:{port}/{database}?user={user}`, with the database and the user percent-encoded. **Copy password** copies the password apps sign in to the port with, and **Rotate password** replaces it after you confirm and copies the new one: new connections need the new password, and open connections keep running. Lunport generates the password, keeps it in the system keychain on this computer, never shows it and never syncs it, and reminds you to clear the clipboard after you copy it. The user name an app sends does not matter, because Lunport signs in to Cloud SQL as the Google account's user. The connection on this computer is not encrypted: Lunport answers an app's request for SSL or GSSAPI encryption with a refusal, so an app set to require SSL cannot connect, and it encrypts the connection to Cloud SQL itself.

A **Prod** database is read-only by default. Lunport starts each of its sessions with Cloud SQL's session read-only lock, which the session cannot undo, so a connection through the port cannot change data. To write, open the running database's connection details and choose **Locked** under **Write lock**. On a Mac that can ask, Lunport asks for Touch ID or the Mac's password; elsewhere it asks you to confirm in a dialog of its own. Writes then stay on for 15 minutes or until you lock them again, and the row says **Writes on · 14:59**, counting down, while they are on. Connections already open when you unlock stay read-only; **Reconnect now** closes the idle ones so that their apps connect again with writes on, and leaves a connection in a transaction or waiting for an answer alone. When writes end, new connections are read-only again, and the connections that came with writes on close as soon as they are idle, at the latest 10 minutes later, when a transaction still open is rolled back. Stopping the database ends the writes too. Dev and Staging databases are not locked. The lock is Cloud SQL's read-only session: on an instance version that does not have it, a connection that carries the lock fails, and the app gets Cloud SQL's own error. While a session is locked, Cloud SQL also blocks the functions and procedures you created in a procedural language.

A running database keeps the settings it started with. When another device changes one that connecting or locking reads (the instance, the route, the Google account, the environment, the grant check or the port), its row says "The database changed on another device. Stop and start it again to apply it." The lock does not wait for that: a running database saved as **Prod** on another device locks its next connections at once, and its writes can be unlocked as any prod database's, while one saved as Dev or Staging there stays locked, and is shown as PROD, until you start it again.

A database that **Requires a PAM grant** shows the grant it needs in its selected **Access grants** details, read again every minute: "Needs a grant: prod-operate", the entitlement with the time its grant is active until, or Google's sentence when the grant could not be checked. A grant that ends within 5 minutes reads "Grant ends in 4 min", with a note that a new one can be requested when it ends, because Privileged Access Manager takes no second request for the scope of a grant that is still active. **Request grant** opens Lunport's **Request a grant** window (see [Google Cloud IAP and OS Login](#google-cloud-iap-and-os-login)) and appears when the grant is missing or has ended. A database reached through a host whose connection begins with a Google Cloud IAP route that requires a grant shows the host's grant on a line of its own, under the database's when the database requires one too, led by the host's alias: "web-1: Needs a grant: prod-operate". It is the grant a connection to that host needs (its first jump host's, when the host is reached through jump hosts), read, warned about and requested as the database's own is, with a **Request grant** of its own, because the host's grant is not the database's. Start asks for it while it connects to the host, and **Request grant** asks ahead of Start. A connection that finds no grant in flight asks in that same window while the app waits. Connections that need the same grant at once, a host's among them, ask once, and **Cancel**, an empty justification or no answer within five minutes refuses the connection with the sentence that quotes the `gcloud pam grants create` command. Google can take a moment to see a new grant: when a connection made within two minutes of a grant becoming active is refused with 403, Lunport tries again every ten seconds for up to two minutes. Each new connection checks the grant, trusting a check for 5 minutes at most and never past the grant's end; connections that are already open keep running when a grant ends.

Credentials come from `gcloud auth login` on each computer, as for IAP hosts, and are not synced. Lunport reads gcloud's credential files again when it renews the certificate it signs in with, about 4 minutes before the old one expires, so a new `gcloud auth login` needs no restart of the database and no reconnect of the apps that are open. When the sign-in has expired or was revoked by then, new connections are refused with "Google sign-in for frank@example.com has expired or was revoked; run `gcloud auth login frank@example.com` and connect again." while the open ones keep running, and the next connection after you sign in again works.

A refusal comes as a sentence, to the page when you start a database and to the app when it connects. Starting a database fails with "Port 6543 is already in use on this computer." when another program listens there (the row says Failed; change the port in the editor and choose **Retry**), with "Lunport runs up to 16 databases at once." past the limit, and at the step that cannot be done, with that step's sentence: "Could not connect through web-1: Permission denied (publickey).", whose reason is whatever a connection to that host would fail with, when the host cannot be connected to; "acme-dev-654321:asia-east1:orders-pg has no private IP, so Lunport cannot reach it through a host." for a database reached through a host whose instance has no private IP; and "acme-dev-654321:asia-east1:orders-pg has no public IP. Choose a host to connect through in its settings." for a database over its public IP whose instance has none. An app that connects to a database saved as Orders is refused with "Wrong password for Orders. Copy the password from Lunport." for another password; "Cloud SQL asked for a database password. Turn on IAM database authentication for acme-dev-654321:asia-east1:orders-pg." when the instance has IAM sign-in off; "Cloud SQL Admin refused the request: The Cloud SQL Admin API is not enabled in acme-dev-654321. Enable it in the Google Cloud console, then try again." when the project has not enabled the API; "Cloud SQL Admin refused the request: Cloud SQL has no instance acme-dev-654321:asia-east1:orders-pg." for a project or an instance that does not exist; "acme-dev-654321:asia-east1:orders-pg is in europe-west1, not asia-east1." when the instance is in another region than the connection name says; "acme-dev-654321:asia-east1:orders-pg is not a PostgreSQL instance." for an instance of another engine; "Lunport could not reach acme-dev-654321:asia-east1:orders-pg: Cloud SQL at 198.51.100.10:3307 did not answer through web-1." when the instance does not answer through the host (the sentence gives the host's own reason instead when it reports one); and "Orders has reached 64 connections." when its port is full.

Up to 16 databases can run on one device, each with up to 64 simultaneous connections; up to 256 databases can be saved.

Databases sync as encrypted library records, port numbers and routes included, where the library uses central sync. **Running state stays on each device:** receiving a database never starts it, and a port's password stays in that computer's keychain. A database reached through a host connects through the same host on your other computers, so each of them needs what connecting to that host needs: a key the host accepts and, for an IAP route, gcloud's sign-in. A computer without them gets the connection's own sentence on the row when it starts the database. A database deleted on another device stays listed only while it runs here, so that you can stop it. Without central sync, that is with no account or an older account that has not moved to central sync, a database stays on the computer where you saved it, and moves into the library by itself once the library uses central sync and has room for it. A library that holds a database needs this release on every device. Devices on older releases stop syncing it until they update. A library that holds a database reached through a host needs this release on every device. Devices on earlier releases stop syncing it until they update. On the same computer, an older release cannot open the library once this release has stored a database in it, and a release from before a database could be reached through a host cannot open it once it holds such a database; removing the database afterwards does not change this.

An AI client can also manage saved databases (see [AI access through MCP](#ai-access-through-mcp)): a database on its public IP while AI access is on, and a database reached through a host only while the client may use that host. A database it started keeps running when you turn off the client's access to its host, because it serves your apps; stop it from the Databases page.

## Connect in Lunport or an external terminal

The in-app terminal is available first on the **Beta** update channel in **Settings → Updates**.

Choose **Lunport (in app)** in **Settings → Connections** for integrated SSH tabs, or select an external terminal. The app terminal is the default for everyone: an external terminal chosen in an older version is set back to it once, and a choice made since then is kept. The Records connection menu changes the same saved preference. Legacy hosts can override it individually. Lunport's built-in SSH engine handles authentication and server identity in either destination. New or changed server fingerprints require a decision in Lunport; compare them against a trusted source before accepting them.

Double-click a ready host or use Quick connect. Each connection opens a separate session tab. In the Records workspace, Library and session tabs share the title bar. Switching to Library, Settings or another tab keeps SSH connected. Tab icons distinguish connecting, failed and ended sessions; the bottom bar shows the active connection's address and status. Closing a running tab asks for confirmation; a completed tab closes immediately. **Terminal options** at the bottom right contains connection details, text-size controls, Copy selection, Reconnect and Disconnect. Closing the app window keeps active sessions running, while quitting, reloading the workspace or installing an update ends them.

An established connection that drops unexpectedly reconnects automatically in the same tab, retaining earlier output. Retries wait 2, 5, 10, 20 and 30 seconds, then pause; an operating-system network-restored event can resume them. Choose **Retry now** or press Enter with terminal input focused to reconnect immediately, or choose **Stop retrying**. The **Automatically reconnect** toggle in Terminal options applies to that tab. Normal shell exits and manual disconnects stay ended. A first failed connection, rejected server identity, cancelled login or authentication failure waits for manual action.

Use **Reconnect** in Terminal options or the bottom bar to replace a live connection; Lunport asks before ending it. Ended sessions show a visible Reconnect button and also accept Enter. Reconnecting opens a new shell and keeps earlier output available for search; queued keystrokes are discarded. Credentials and server identities still use the normal authentication and verification flow. Use a remote tool such as tmux when commands must survive disconnection.

In **Settings → Connections → In-app terminal**, choose the terminal text size and cursor preference. App color themes apply to the terminal; dark presets include their ANSI colors. Text size and theme changes apply to open sessions without reconnecting. **⌘F / Ctrl+F** searches retained output in a floating panel without resizing the remote terminal; Enter / Shift+Enter selects the next / previous match, and Escape closes Find and returns to terminal input. **Ctrl+Tab / Ctrl+Shift+Tab** switches workspace tabs. When a tab has keyboard focus, Left / Right and Home / End move between tab labels; Enter or Space activates one. **⌘ / Ctrl +**, **−** and **0** adjust or reset terminal text size. Quick connect is **⌘K** on macOS; inside a terminal on other platforms use **Ctrl+Shift+K** so Ctrl+K remains available to the shell. Use normal copy/paste shortcuts or **Terminal options → Copy selection**. Remote clipboard writes are disabled.

Up to eight session tabs can be open. Retained history and queued data are bounded; if the terminal cannot consume output, it reports the interruption rather than retrying keystrokes.

Use a key from the local vault, a saved password or an interactive authentication prompt. Passwords, key passphrases and two-factor codes appear in Lunport’s **SSH authentication** window, with the requesting host and username. Answers apply to the current connection; cancelling or closing the terminal abandons its questions. Shell input continues in your preferred terminal.

In the Records host editor, choose **Authentication → Password**. Leave the password unset to enter it in Lunport when connecting, or choose **Save password**, enter it and save the host. Saved SSH passwords use protected local credential storage and join end-to-end encrypted library sync when enabled. The editor shows saved status without reading or revealing the saved password; **Replace password** and **Remove saved password** take effect when you save changes. If credential storage fails after creating the host, retry **Save changes** without creating another host.

The SSH engine supports `ProxyJump`; `ProxyCommand` connections are not supported. It signs with keys kept in Lunport, so an external `IdentityFile` must be imported or moved into the vault before this engine can use it. A host relying on an implicit `~/.ssh/id_*` key must select its key explicitly.

### Google Cloud IAP and OS Login

A host on a Compute Engine instance can be reached through Identity-Aware Proxy TCP forwarding instead of a public address, without `gcloud` running. In the host editor, choose **Google Cloud IAP** under **Connect via** in place of **Address**, then enter the **Instance**, the **Project** and the **Zone**; the instance takes the address's place beside the port. **Google Cloud options**, folded until you open it, holds the Google account, **OS Login**, the Privileged Access Manager grant check and the network interface (`nic0` for the first). The host is then reached through the tunnel instead of at its address, and saving it with **Address** again removes the route. **New IAP host** on the **Google Cloud** page, under **Cloud** in the Library sidebar (or **⌘N / Ctrl+N** there), opens a new host with Google Cloud IAP already chosen. A host with a route says **IAP** on its card, and its details show the instance and project in place of the address. The tunnel goes to the host's port on the instance, so the instance's firewall must allow Google's IAP range `35.235.240.0/20` on that port, and the Google account needs `roles/iap.tunnelResourceAccessor` on the instance. Jump hosts still work: an IAP host can be the first hop of a chain, but not a later one.

A route is saved with its host. In a library that uses central sync it syncs wherever the host does (the editor says "Saved with the host, so it syncs wherever the host does."), so the same host connects through IAP on your other computers as soon as their gcloud is signed in. Without central sync, that is with no account or an older account that has not moved to central sync, a route stays on the computer where you saved it, and the editor says "Saved on this computer only." Routes already saved on a computer, by an earlier release or before it used central sync, move into the library by themselves once it uses central sync, for the hosts the library has: at the first sync after the computer has read the library's latest changes. Where the library already holds another computer's route for the same host, that route is kept and replaces this computer's copy. A route the library has no room for stays on that computer, and the **Google Cloud** page says so; a new save that would not fit is refused with a sentence that says what to remove. Deleting a host deletes its route. Devices running Lunport 1.12 or earlier stop syncing a library once it holds a route, until they are updated. On the same computer, Lunport 1.12 cannot open the library once it has held a synced route or the memory of a grant requested from Lunport, or once moving it to central sync (publishing it or adopting one) kept routes this computer had saved, or the record of one it had removed; releases before 1.12 cannot open it once it has held any route. Removing routes afterwards does not change this.

Credentials come from `gcloud auth login` on each computer: Lunport reads the files gcloud keeps under `~/.config/gcloud` (`%APPDATA%\gcloud` on Windows, or `CLOUDSDK_CONFIG`) and refreshes access tokens itself. Sign-ins are per computer and are not synced. **Google account** chooses which signed-in account the route uses, from the accounts gcloud has on the computer; leave it on gcloud's active account to use whichever account is active on each computer. When a sign-in has expired, the connection says so and `gcloud auth login <account>` fixes it.

**OS Login** registers the host's vault key with OS Login when it is not there yet and checks that the host is saved with OS Login's username for the account. While the route uses OS Login, **Use OS Login username** under **Username** fills in that username for the route's account and project; it is saved with the host when you save, and the project must have OS Login enabled. The **Require a Privileged Access Manager grant** switch reveals the **Entitlements** (for example `prod-operate, prod-admin`), their **Location** and a **Default grant** length. One of the entitlements must hold an in-flight grant before Lunport opens the tunnel. The default length (30 minutes at first) is what a request starts from until you have asked for that entitlement; it is saved with the route, so it syncs. When none is in flight, a connection you start asks you for one in Lunport's **Request a grant** window: the justification and the duration in minutes, prefilled with what was last asked for on that entitlement (the route's default length when nobody did); **Request** (or Enter) requests the grant on the first entitlement as you, waits until it is active and goes on connecting, while the terminal reads `Waiting for you to request a Privileged Access Manager grant in Lunport.` **Cancel**, an empty justification or no answer within five minutes fails the connection with the sentence that quotes the `gcloud pam grants create` command, as before. Several connections that need the same grant at once (every tab reconnecting after a network drop, a tunnel starting with a tab) ask once. IAP can take about 1½ minutes to see a fresh grant: for two minutes after a grant became active, a refused tunnel is tried again every ten seconds and the terminal says so once; a refusal after that explains the delay. AI requests through MCP ask in the same window, in Ask and Auto-log mode alike, and the window names the AI client; in Auto-log the client's commands then run without per-command review while the grant lasts. Lunport's own server-identity check in the host editor never requests a grant; it gets the refusal.

The details of a host whose route requires a grant show an **Access grant** section: which entitlement holds an active grant and until when (or that one is activating, or that none is), refreshed every minute, and **Request grant…**, which opens the same form and is off while a grant is active. The justification and the length you last used are remembered on this computer only, so requesting a grant never edits the route that syncs. A tunnel through a host that needs a grant (the host itself, or its first jump host) shows that grant on its row in **Tunnels**, refreshed every minute, asks for one when it starts without one, and says so when it stops because the grant ended.

For a host with a route, **Check through IAP** takes the place of **Check port** in its details. It opens a tunnel to the instance's port with the route's Google account and closes it at once, and gives up after 20 seconds; it says whether the port was reached through IAP and how long that took. When IAP refuses the account the check says so, and for a route that requires a grant it adds that you can request one; an expired sign-in is named with the command that fixes it. Anything else that stops the tunnel, such as a firewall that does not allow IAP's range to the port, is reported with its reason. The check never requests a grant or asks you to sign in, and it tries no SSH, so login and server identity are verified separately.

The **Google Cloud** page sits under **Cloud** in the Library sidebar, where other cloud providers will join it, and has three tabs; it edits no route, since routes are edited with their hosts.

**Accounts** is gcloud on this computer. Lunport finds gcloud on its own `PATH`, in the places gcloud's installers use (Homebrew, `~/google-cloud-sdk`, the Linux packages, snap, the Windows installer's folders) and, last, by asking your login shell once; the tab says where it found it, or how to install it, with **Check again**. Each account gcloud has credentials for is listed with whether its sign-in works (signed in, expired, or could not be checked), a **gcloud active** badge and how many routes use it; an account a route names that this computer has no sign-in for appears as **Not signed in on this computer**. Lunport runs gcloud for you here, and every change applies to gcloud itself, so to `kubectl`, Terraform and every other tool on the computer that uses it. **Sign in again** opens your browser (`gcloud auth login <account> --force --no-activate`) and changes no other account; **Add account** signs in a new account the same way; neither makes the account gcloud's active one. **Make active** (`gcloud config set account`) makes an account gcloud's active one after you confirm. **Remove…** (`gcloud auth revoke`) asks first, then revokes the sign-in at Google and deletes its credentials from this computer; Google may also end that account's gcloud sign-in on your other computers. While gcloud waits for the browser, the window offers **Open the sign-in page** in case the browser did not open, and **Cancel**. Without gcloud, the actions are off and the commands are shown to run in a terminal.

**Access** is Privileged Access Manager on its own. A grant belongs to your Google account: until it ends, every tool that uses the account has its roles. The tab lists every entitlement you may request in the places Lunport looks, with where it lives, the roles it gives, the longest grant it allows, whether an approver must approve it, the hosts whose routes need it, and its grant: active until a time, activating, awaiting approval, or none. **Request grant** asks for one as that account with a justification and a duration, prefilled with what was last asked for on that entitlement; it is off while a grant is active, activating or awaiting approval. For an entitlement an approver approves, the request is sent and the row reads **Awaiting approval** until the approver acts; Lunport refreshes the tab every minute. **Where Lunport looks** lists the projects your routes use (with the account each route uses) and the scopes you add with **Add scope**: a project, folder or organization, its location (`global` usually) and the Google account to ask as (empty is gcloud's active account on each computer). Added scopes and the last justification and length used for each entitlement sync with the library where it uses central sync, so your other computers offer the same. Lunport never ends a grant early.

**IAP hosts** lists each host with a route, with its project, instance, zone and account; choosing a host opens its editor. A route the library has no room for is marked **Saved on this computer only: the library has no room for this route**; one still waiting to move in for another reason, such as paused sync, is marked **Saved on this computer only**.

Devices running Lunport 1.13.0-1 or earlier stop syncing a library once it holds a search scope or the memory of a grant requested from this release (the first grant requested from Lunport writes one), until they are updated; their own data stays intact. On the same computer, Lunport 1.13.0-1 or earlier cannot open the library once this release has stored a scope or a grant memory in it.

A dropped network connection is reconnected inside the tunnel for up to 15 minutes; the SSH session survives it as long as its keepalive allows (with the host's defaults, 30 s × 3 missed, about a minute and a half), and when the tunnel ends the connection says why.

The command-line entry point is `lunport connect <host>`. Windows terminals use `lunport-cli.exe`, installed beside `lunport.exe`.

## Import and manage keys

Open **Keys → Import private key → From a file** to choose a supported OpenSSH private key with the system picker. You can also paste it. Lunport copies the key into its encrypted local vault and preserves the original file. Passphrase-protected keys retain their protection.

To change a key's name, select it in **Keys**, choose **Rename**, and save the new name. The key ID, fingerprint, private material and host references stay the same. Account key names sync to your other devices; a conflicting or deleted key must be resolved before renaming.

Central library sync includes managed SSH private keys by default after you sign in and unlock sync. There are no per-key sync switches or private-key download steps. The Keys page offers **Set up automatic sync** until this library has completed account setup and migration. Generating or importing a key then includes it in that encrypted library. Hardware and external-agent keys keep their private material on their original device. Saved SSH passwords sync with their hosts; separately stored key passphrases stay on each device.

Vault keys serve Lunport's own connections. Importing a key leaves its original file in place, so other programs keep using that file.

## Local use without an account

New installations open a local library immediately. Add and edit hosts, manage keys, import SSH configuration and connect to your servers without signing in. These actions do not enroll the device or upload your library to the sync service. SSH connections still need access to their destination servers.

Sync is optional. Open **Sync** when you want to connect your devices; choose **Sign in and sync with Passkey**, then set or enter your sync unlock password. Library sync starts automatically after successful unlock. Until then, locally managed SSH private keys remain in the encrypted local vault. Once library sync is enabled, managed keys join the encrypted library by default.

An existing synced library retains its device approval, recovery and migration checks. Local use does not bypass a revoked device or an unfinished safety review.

## Sync your library

Passkey account sync is available on macOS, Windows and Linux.

Open **Sync** in the upper-right toolbar, or **Settings → Local data → Open sync**. The account-service URL starts blank: deploy your own Cloudflare or Docker service, enter its HTTPS URL and choose **Sign in and sync with Passkey**. Local use needs no account. Passkey needs no external identity provider; OIDC remains optional.

On the first device, create and confirm a **sync unlock password** of at least 12 characters. Lunport prepares and syncs your encrypted library automatically. Hosts, Groups, tunnel rules, Google Cloud IAP routes, saved Cloud SQL databases, saved SSH passwords and managed SSH private keys are included. The server stores encrypted library content.

On another device, sign in to the same account on the same server, then enter the same sync unlock password once. Lunport securely connects the device, downloads your library and merges local records automatically. Imported host references, tunnel rules, Google Cloud IAP routes and the hosts that saved Cloud SQL databases connect through are remapped together. No pairing code is required. Passkey signs you into the account; the sync password unlocks encrypted data inside the app.

The former sync-code controls are removed. To change an already selected service, edit its URL and choose **Change server and restart**. This opens a separate empty local library and closes terminal sessions. Reimport your SSH config explicitly; old account, Vault and backup contents are not silently uploaded to the new service. First-time sign-in from a local library keeps that library.

New and imported records then sync with the library. You can edit cached records offline; changes queue until the next connection. Managed SSH private keys and saved SSH passwords are included automatically. The relay receives ciphertext. Changing or removing a saved SSH password also syncs. Passwords remain bound to the host identity, address, port and username; changing those connection settings requires saving the password again. Previously saved passwords without that binding must be saved again once. Each device still confirms server fingerprints before using credentials. When your library already has a host's fingerprint, the trust window says when it was saved; a server presenting a different fingerprint gets the changed-key warning, and **Accept new key** replaces the saved fingerprint for all your devices.

Use the account device controls to revoke a lost device. Revocation blocks subsequent authenticated sync; it does not erase content already decrypted on that device. Save your sync unlock password in a password manager. It is not sent to the server and cannot be recovered through Passkey sign-in.

The relay can run on Cloudflare Workers or your own server with Docker Compose. See [server configuration and deployment guides](central-server-configuration.md). Relay URLs require HTTPS; localhost HTTP is allowed for development.

## AI access through MCP

Open **Settings → AI access**, enable access and choose the hosts or Groups a client may use. An explicitly allowed Group includes subgroups and current or future members, including synced hosts. Moving a host out removes that Group permission; individual grants remain until removed separately. Group permissions are local to this device and library, use stable IDs, and are independent of the display name. Renaming retains permission; another Group with the same name receives none. Under **Connect an AI tool**, select Codex, Claude Code, Claude Desktop, Cursor or VS Code and choose **Add**. Codex and Claude settings are backed up before the app saves its entry; Cursor and VS Code open their own installation review. Existing unrelated servers and settings are preserved. Adding a tool does not grant host permissions or change command review.

**Allowed hosts** shows the effective host count and separate **Groups** and **Hosts** tabs. Search or filter by access status; select a Group’s host count to review its members. Each row shows **Allowed**, **Not allowed**, or **Partial** for a Group covered only by member grants, with its access source and member count. **Manage access** opens the inherited grant or adds a separate grant that survives its removal. **Remove grant** removes only that direct grant; other Group or individual grants continue to apply. Raw record IDs are omitted from normal rows but still work in search.

**Configured** means the settings were saved, not that the client is connected. Start a new Codex or Claude Code session, or quit and reopen Claude Desktop, to load the server. Cursor and VS Code finish installation in their own UI. **Refresh status** checks the local settings again; **Repair setup** can update an existing Lunport entry. A conflicting server name, malformed settings or a managed settings symlink is left untouched, with manual setup available.

For another agent, open **Manual setup & other agents**. Copy or export the JSON `mcpServers` configuration, Codex TOML or VS Code JSON. The same area provides the executable path and `--mcp` argument separately, plus optional Codex/Claude Code terminal commands. These configurations connect a local stdio MCP client on this computer. They register the server as `lunport` and export as `lunport-mcp.json`, `lunport-mcp.toml` or `lunport-vscode-mcp.json`. Use the executable path shown by the app.

The Records adapter uses an OS-authenticated local session broker. It can start Lunport in the background; approvals and server trust decisions appear in the app when needed.

| Tool | Behavior |
| --- | --- |
| `list_hosts` | List hosts allowed individually or through a Group. |
| `get_host` | Read sanitized public settings for a permitted host, including its Google Cloud IAP route when it has one. |
| `ssh_exec` | Execute a bounded command under Ask or explicitly acknowledged Auto-log. A new or changed server key, and a grant the host needs, are asked in Lunport's windows first. |
| `ssh_sudo_exec` | Run one command with sudo. Lunport always asks you to approve the command, including in Auto-log, and opens a separate native sudo password prompt only when needed. The client never receives a terminal input channel. |
| `scp_upload` | Copy one local file to a permitted host through Lunport's SSH connection. Ask reviews both paths; Auto-log skips that review. |
| `scp_download` | Copy one remote file to an absolute local path. An existing local file is never replaced. Ask reviews both paths; Auto-log skips that review. |
| `create_host` | Propose public connection settings for your review. Saving does not grant AI access or trust a server key. |
| `verify_host_key` | Verify a permitted host's fingerprint, with an in-app trust decision for a new or changed key. |
| `update_host` | Propose changes to a permitted host's public connection settings; Lunport shows each change as old → new and asks before saving. Changing the address clears the pinned server key, as the editor does. |
| `set_transport` | Propose a permitted host's Google Cloud IAP route, or changes to it (a field given replaces that field only; `pam` sets or removes the grant check); Lunport asks before saving. |
| `remove_transport` | Propose removing a permitted host's route, so it is reached at its saved address again; Lunport asks before saving. |
| `list_tunnels` | List the tunnels through permitted hosts, with their state on this computer and where a running tunnel listens. |
| `create_tunnel` | Propose a local, remote or SOCKS5 tunnel through a permitted host; Lunport shows who could reach its listener and asks before saving. |
| `update_tunnel` | Propose changes to a tunnel (a field given replaces that field only); Lunport shows each change as old → new and asks before saving. A running tunnel must be stopped first. |
| `delete_tunnel` | Propose deleting a tunnel; Lunport asks first. A running tunnel must be stopped first. |
| `start_tunnel` | Start a saved tunnel under Ask or Auto-log, as `ssh_exec` connects, and answer where it listens. It keeps running until stopped; Lunport stops it when AI access to its host ends. |
| `stop_tunnel` | Stop a running tunnel through a permitted host, including one you started, without asking. |
| `list_databases` | List the saved Cloud SQL databases the client may use, with their route, their state on this computer and where a running one listens: databases on their public IP, and databases reached through a permitted host. No port password is returned. |
| `create_database` | Propose a saved database, on its public IP or through a permitted host (`via_host`); Lunport shows every setting, the route included, and asks before saving. |
| `update_database` | Propose changes to a database (a field given replaces that field only; `via_host` set to null returns it to its public IP, `pam` set to null removes the grant check); Lunport shows each change as old → new and asks before saving. A running database must be stopped first. |
| `delete_database` | Propose deleting a database, with its port password on this computer; Lunport asks first. A running database must be stopped first. |
| `start_database` | Start a saved database under Ask or Auto-log, as `start_tunnel` starts a tunnel, and answer where it listens. It keeps running until stopped, also after AI access to its host ends. |
| `stop_database` | Stop a running database the client may use, including one you started, without asking. |

For example, a client can propose `create_host` with `{"alias":"web","hostname":"server.example.com","user":"deploy","port":22}`. Review the settings in Lunport, then allow that host in AI access, or save it in an already allowed Group, before inspection, fingerprint verification or command execution. The native creation review shows whether existing Group permission applies. Creation fields cannot supply passwords, private keys, host-key pins or AI permission grants.

To change a host the client may use, it proposes `update_host` with `{"alias":"web-1","hostname":"192.0.2.8"}`, and to reach it through IAP, `set_transport` with `{"alias":"web-1","project":"acme-prod-123456","zone":"asia-east1-b","instance":"jumpbox","pam":{"entitlements":["prod-operate"]}}`; each opens Lunport's approval window with the fields that would change, and nothing is saved without your click, in Auto-log mode too. Moving a host between Groups, its server key, passwords and private keys stay out of reach of these tools.

To reach a database behind a server, a client proposes `create_tunnel` with `{"name":"Database","host":"web-1","port":15432,"target_host":"db.internal","target_port":5432}` and then `start_tunnel` with `{"tunnel":"Database"}`. Saving always opens the approval window, in Auto-log mode too. Starting opens it in Ask mode; Auto-log starts without it. In both modes a new or changed server key opens the trust window, and a grant the route needs the **Request a grant** window, as for `ssh_exec`; the call keeps waiting while one of Lunport's windows is open. The answer names the address to connect to, such as `127.0.0.1:15432`. Tunnels are named by their ID or exact name, and only tunnels through hosts the client may use are listed or changed.

To reach a Cloud SQL database, a client proposes `create_database` with `{"name":"Orders","connection_name":"acme-prod-123456:asia-east1:orders-pg","environment":"prod","via_host":"web-1"}` and then `start_database` with `{"database":"Orders"}`. `via_host` is a host the client may use, by its ID or exact alias; without it the database is reached over its public IP. Without `local_port` the database gets the first free port from 6543 up, as the Cloud SQL page proposes one. Saving and deleting a database always open the approval window, which lists every setting, and changing one opens it with each change listed as `old → new`, in Auto-log mode too. Starting opens it in Ask mode; Auto-log starts without it, and the windows on the way then say that the database starts without review. In both modes a server key of the host that this computer has not verified opens the trust window before the database starts, and a grant the database or its host needs the **Request a grant** window, as for `ssh_exec`, each naming the AI client. The call answers once the port runs or fails, and after 90 seconds it answers that the database is still starting, for example while one of Lunport's windows waits for you; `list_databases` then shows how it goes. The answer names the address to connect to, such as `127.0.0.1:6543`. No tool returns or accepts the port password: apps sign in with it, and you copy it from the Cloud SQL page. Databases are named by their ID or exact name, and a database reached through a host is listed or changed only while the client may use that host.

`verify_host_key` accepts a host ID or exact alias; the client cannot supply a trust decision. You can also use **Edit host → Server identity → Verify server fingerprint**. Verification stops before destination login or remote commands. Jump hosts may need their own credentials. A matching saved fingerprint does not prompt again; a changed destination, route, permission or pin requires verification again.

Ask reviews the exact command, transfer paths, tunnel start or database start; Auto-log skips that operation review. `ssh_sudo_exec` always requires a separate command review. In both modes Lunport asks in its native windows whatever a connection of yours would ask: passwords, key passphrases and 2FA, a server key it has not verified, a changed server key (with its **Server identity changed** warning), and a Privileged Access Manager grant. Each window says which AI client asked, and in Auto-log what then runs without per-operation review. When `ssh_exec`, `ssh_sudo_exec`, either SCP tool, `start_tunnel` or `start_database` (for the host the database goes through) reaches a server key Lunport has not verified, Lunport shows its fingerprint before any login to the host. After **Trust this key** (or **Accept new key**) the same call continues; **Cancel**, **Refuse**, closing the window or no answer within two minutes ends the call, and nothing is saved. Authentication answers and command output are not retained in the public audit log. This permission gate covers Lunport MCP requests; other local programs still have their own operating-system access.

For occasional privileged work, call `ssh_sudo_exec` with `alias`, a shell `command` without a `sudo` prefix and optional `timeout_seconds` (1–300; default 60). Lunport shows the host, route and full command before asking you to allow it once. It runs that text through `/bin/sh -c` under sudo, so the remote sudo policy must permit the shell. If sudo requests a password, enter it in Lunport's **Sudo authorization** window; the answer is sent only to this command and is not saved or returned to the AI client. The PTY merges standard output and error into the tool's `stdout`; `stderr` is empty. The command's own standard input is closed, and only one password answer can be sent; multi-prompt sudo authentication is not supported. A second prompt ends the request. For repeatable automation, configure a dedicated remote account and narrowly scoped sudoers commands, then use `ssh_exec` with `sudo -n`; a needed password makes `sudo -n` fail rather than wait. Lunport's sudo review is a workflow boundary, not a remote privilege boundary: an account that can already run sudo through `ssh_exec` retains that ability. Set the account's actual privileges on the remote host.

`scp_upload` and `scp_download` accept `alias`, `local_path`, `remote_path` and optional `timeout_seconds` (1–3600; default 300). The local path must be absolute; each call transfers one regular file using the remote host's SCP program. Set the single-file limit under **Settings → AI access → File transfers** from 1 to 10,240 MiB; it defaults to 1,024 MiB on each device, and changing it cancels active AI transfers. For example, `scp_upload` can take `{"alias":"web-1","local_path":"/tmp/report.txt","remote_path":"/srv/report.txt"}`. Downloads are staged in the destination directory and saved only after the transfer completes; they fail if the local target already exists. An upload can replace an existing remote file, and an interrupted upload can leave a partial remote file. Transfers follow the same host access, Ask/Auto-log, server-key, credential and grant rules as `ssh_exec`; the activity log records paths and outcome, not file contents.

**AI activity** in the Library sidebar lists what AI clients asked Lunport to do through its tools, newest first and grouped by day: commands, file transfers, tunnels started, stopped, created, changed or deleted, databases started, stopped, created, changed or deleted, hosts proposed or changed, routes set or removed, and server keys verified. Reading the library (`list_hosts`, `get_host`, `list_tunnels` and `list_databases`) is not listed, and neither is a request Lunport turned down before acting on it, such as one with input it rejects or for a host it cannot find. Each entry says what was asked and on which host, its result, the AI client Lunport observed, how the request was reviewed and when it finished; a request about a database names the database, and the host it goes through when it has one. A result is one of four: **Succeeded**; **Failed**, for a command that ran and ended badly, such as **Failed · exit 1**, **Timed out** or **Connection lost**; **Not run**, when the request stopped at a decision, **Refused by you**, **No answer**, **Canceled** or **Not allowed**, naming the Lunport window where it stopped; and **Error**, with the reason it gave. A refusal or an unanswered window is never counted as an error, but for one case: when you cancel or refuse a window that opens while a database an AI client started is starting, such as **Request a grant**, a password, passphrase or 2FA question, or a changed server key, the entry reads **Error**, with the sentence the start ended with. Being allowed to run never counts as success: an entry without a recorded ending reads **Result unavailable**, and a tunnel or a database that was still connecting when Lunport answered reads **Still connecting**. Search actions, hosts and clients, and narrow the list by AI client, host, action (commands, file transfers, tunnels, databases, host and route changes, server keys) or result. The list shows 100 entries at a time, with **Show 100 more**, and Lunport keeps the latest 1,000 AI entries on this computer, across restarts. Open an entry for the full command or transfer paths, its result and review in words, the request and completion times with seconds and this device's local time zone, the request and host IDs, a command's termination, exit code and signal, the recorded outcome and the requester attribution, which keeps what the client says of itself apart from what Lunport observed. Entries without a usable timestamp show **Time unavailable**. **Show host** opens the host in the library, unless it is no longer there (an entry about a database on its public IP names no host, and has none to show), and **Copy command** or **Copy transfer paths** copies the recorded action. Command output and authentication answers are never recorded, and terminal sessions and key deploys are not listed.

**Settings → AI access → Activity** shows the latest entry, such as *Last: today 14:20 · Ran a command on web-1 · Succeeded*, with **Open AI activity**.

## Updates and help

**Settings → Updates** shows the installed version, release notes, download progress and Stable/Beta channel. Switching from Beta to Stable keeps the installed version until a newer stable version is available. Installing an update restarts the app and ends active sessions.

Lunport asks `lunport.ysya.dev` for updates first, which redirects to the release manifests on GitHub, and asks GitHub directly when that address cannot be reached or answers with an error. Either way, an update installs only with Lunport's signature.

On macOS, an app bundle installed under an earlier name is moved to `Lunport.app` when the updated app starts, leaving a link at the old path; macOS may request installation permission once. A cancelled or incomplete move can be retried in **Settings → About → Finish the Lunport rename**, without reinstalling. A conflicting app at the destination is never overwritten.

**Settings → About** contains the Lunport identity, installed version, project, releases, issues and license links. On macOS, **Lunport → About Lunport** also opens the native panel. Local diagnostic logs are available in **Settings → Diagnostics** in Records, or **Discovery & checks** in Legacy.

### Recover host settings from an old local workspace

In **Import**, choose the old Lunport `sync-state.json`, review the hosts, then confirm. On macOS, the original file is `~/Library/Application Support/dev.ysya.lunport/sync-state.json`; switching servers preserves it while the new workspace lives in a separate `server-workspace-*` folder. Choose the original file on any device that still has the host cache. The old relay does not need to be available.

This restores host aliases, addresses, users, ports, jumps, timeouts, tags and notes. Groups retain their hierarchy, defaults and host membership. The import uses new local host and Group identities and preserves the source file. Assign new SSH keys in the host editor and confirm server fingerprints when connecting; old account state, key material and trust approvals are excluded. After reviewing the local hosts, finish encrypted library setup to sync them to the new account.

### Move hosts and Groups between devices

Open **Hosts → All hosts → More library actions → Export hosts and Groups…** to save `lunport-hosts.json`. If a server change left the old library in the original workspace, choose **Choose a saved workspace…** instead. Export works offline without signing in and reads cached host settings; it does not contact the retired relay or open the key Vault.

On the destination device choose **Import hosts**, select the exported JSON, review the hosts, then confirm. Group names, hierarchy, defaults and host membership are retained, including empty Groups. Jump-host relationships, tags and notes are also retained. Older host-only exports still import, but require a new export from the source workspace to recover Groups. SSH private keys, old key bindings, server fingerprint approvals, imported commands and account credentials are excluded. Assign SSH keys and verify server fingerprints before connecting. Saved SSH passwords are also excluded. Source workspaces remain in place. Host exports contain server addresses and notes, so keep them private.
