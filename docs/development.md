# Developing Lunport

Lunport uses Tauri 2, Rust, React, TypeScript and Vite, with Tailwind, shadcn/ui, TanStack Query and Zustand. Privileged file access and SSH operations run in Rust; the WebView has no filesystem or shell-execution permission. The Records workspace uses the built-in SSH engine; Legacy retains OpenSSH configuration tooling.

## Local setup

Install Rust through mise or rustup, Node and pnpm. macOS needs Xcode Command Line Tools. Linux needs the Tauri platform dependencies, including `libwebkit2gtk-4.1-dev`, `build-essential`, `libssl-dev` and `librsvg2-dev`.

With mise, run `mise install` for the project's Rust toolchain. Prefix commands with `mise exec --` when mise is not active in your shell.

```bash
pnpm install
pnpm tauri:dev
pnpm build
pnpm test
cd src-tauri
cargo test --locked
```

Some backend tests need a scratch OpenSSH server or platform-specific facilities; credential-service tests can touch the OS keychain. The safe suite and platform-specific checks are defined in [the SSH engine workflow](../.github/workflows/test-engine.yml) and [the Windows workflow](../.github/workflows/test-windows.yml).

## Test feedback time

For an edit to one component or Rust module, run its tests first, then leave the complete platform suites to CI:

```bash
pnpm test src/components/HostEditor.test.tsx
cd src-tauri
cargo test --locked --lib sync::central::server_change -- --test-threads=2
```

Development/test builds optimize the existing OpenSSH PEM/base64 parsers as well as the crypto primitives. Application code keeps debug assertions and overflow checks; fixture sizes and validation remain unchanged. CI runs the actual Production and Development release-library boundaries in parallel with the complete debug suites. Windows runs each migration/publication/console test once in the complete suite; the separate Win32 handle/DACL probe remains.

## Isolated Development profile

`pnpm tauri:dev` runs **Lunport Dev**. `pnpm tauri:build:dev` builds a release-mode Development bundle. The Development profile uses `dev.ysya.lunport.dev`, the `Lunport Development` credential service and a sandbox home under its data directory. It can run beside Production. Writes remain in that sandbox; updater and login integration are disabled. Selected external import sources are read and copied, preserving the originals.

Records connections use the built-in engine. A build whose Tauri configuration disagrees with its compiled profile on the identifier, product name or main binary refuses initialization. Tauri does not embed the publisher, so only the tests compare it with `identity.rs`.

An ordinary `pnpm tauri build` uses the Production profile. Keep the two profiles separate when validating existing data.

## SSH forwarding

`ssh/forward.rs` defines the engine-neutral forwarding contract. The existing russh connection owns TCP listeners, remote forwarding registrations and SOCKS5 CONNECT relays, including jump chains, cancellation and bounded stream concurrency. `session/tunnels.rs` keeps human-started runtime handles outside persistent state and joins the broker's quit barrier. The main-window commands reuse the existing connector, native authentication and host-key policy; this feature adds no agent forwarding, MCP tool or credential delivery to the WebView.

Each definition is an optional account `meta` record named `tunnel:<16-hex-id>`, with payload `{schema: 1, rule: ...}`. Host and account protocol schemas stay unchanged. Separate records give unrelated definitions independent LWW revisions; UI mutations compare the complete displayed rule. Newer opaque revisions block edits and starts. Older clients retain these envelopes without changing their contents. Local definitions live in `local.tunnel_rules`; local state format **6** protects that field from downgrade. Joining an account publishes local definitions after an authenticated baseline, while leaving remaps preserved host IDs. Code rotation re-encrypts the existing metadata through the generic rotation path. Live listeners, ports, errors and active connection counts never sync or persist.

For a native Development preview, run `python3 scripts/preview-ssh.py --forwarding`, import its disposable host/key and use the printed HTTP destination as a tunnel target. The fixture remains loopback-only and stops its SSH sessions on Ctrl-C.

Validation: `cargo test --locked --lib ssh::engine_tests::forward` uses disposable OpenSSH servers for all three forwarding types, binary traffic, TCP half-close, active-stream cancellation, occupied ports, denied remote requests, remote auto-port allocation, DNS via SOCKS and a two-hop chain. `scripts/validate-group-order-compat.sh` runs an injected test against the unmodified published v1.2.0 merger to check opaque rules and tombstone retention. The normal Rust suite also covers rule merge, future versions, account detach, runtime isolation and quit barriers; frontend tests cover independent starts, missing hosts, remote changes and routes.

## Google Cloud IAP transports

`src-tauri/src/gcp/` holds everything Google: `relay.rs` is the SSH Relay v4 wire format and `iap.rs` the WebSocket tunnel with the reconnect rule gcloud documents for its `_OnClose` (a failure without a Close frame, or close code 4004, is reconnected by session id for up to 15 minutes, every attempt bounded; any other Close frame ends the tunnel, and the engine repeats the reason), pumping each direction independently, both ported from gcloud 590's `iap_tunnel_websocket*.py` under the Apache License 2.0 recorded in `gcp/NOTICE.md`; `auth.rs` reads gcloud's credential files and refreshes tokens without running gcloud; `oslogin.rs`, `pam.rs` and `rest.rs` are the calls the broker makes before connecting (reqwest for OS Login, Google's client library for Privileged Access Manager, below). The engine's `Hop::transport` chooses TCP or a tunnel for the first hop only (`russh_engine.rs` hands the tunnel stream to its existing handshake), and `HostDirectory::prepare` runs the PAM grant check and OS Login between the resolve and the connect, outside the directory lifecycle lock.

Privileged Access Manager goes through Google's Rust client library, `google-cloud-privilegedaccessmanager-v1`, with `google-cloud-auth`, `google-cloud-gax` and `google-cloud-wkt`: `gcp/credentials.rs` implements the library's `CredentialsProvider` over Lunport's own token source, so the gcloud sign-in files and the account rules stay Lunport's and the library only adds the `Authorization` header. `gcp/pam.rs` holds the grant model and `request_and_wait`, the one request flow the connect (`session/record_directory.rs`) and a host's Access grant and Request grant (`session/transports.rs`: `transports_pam_status`, `transports_pam_request`) share. A connection that needs a grant asks for it through a question of its own kind, `QuestionKind::Grant` (`session/protocol.rs`), which the authentication window shows as the Request-a-grant form (`AuthenticationWindow.tsx`, a five-minute deadline); connections that need the same grant at once share a gate (`session/grants.rs`), and a tunnel IAP refuses with 4033 within two minutes of the grant becoming active is retried (`session/connect.rs`). In tests the library client is built `with_endpoint(server.url())` against mockito; the library sends enums as numbers and `$alt=json;enum-encoding=int`, so PAM mocks match `callerRelationship=1` and otherwise take any query. The MCP tools `update_host`, `set_transport` and `remove_transport` (`mcp/management.rs`) build a change on a snapshot, show it in the approval window as rows of `old → new` under a proposal `kind`, and save on consent against the host's revision or the transport as it was.

`session/transports.rs` holds the commands behind the host editor and a host's details; the Google Cloud page (`GoogleCloudPanel.tsx`, under the sidebar's Cloud section, `src/lib/cloud.ts`) has three tabs, `GoogleAccountsTab.tsx`, `PamAccessTab.tsx` and the IAP hosts list, and edits no route. `transports_oslogin_profile` backs **Use OS Login username**, `transports_pam_status` and `transports_pam_request` a host's Access grant and Request grant (the request takes an optional `entitlement` the route lists, answers with that entitlement and remembers the justification and length in the device-local grant memory), `gcp_accounts` lists the accounts gcloud holds credentials for (`legacy_credentials/*/adc.json` under its config directory, read without writing there) and checks each sign-in through the token source (the editor's account picker reads the same answer), and `transports_iap_probe` is **Check through IAP**: it opens an IAP tunnel to the route's instance and the host's port, closes it at once, is bounded at 20 s, shares the port check's limit of four checks at once and asks for no grant and no sign-in. `transports_save` and `transports_delete` are gone: the host editor sends a route with its host, as the optional `route` argument (`RouteChange`: the route as displayed, `expected`, and the one to save, `kind`) of `records_host_create` / `records_host_update`, applied in the same edit (`transports::apply_route_change`), and deleting a host removes its route in that edit (`transports::remove_route`). MCP writes through `transports::set` itself.

A route is a `Meta` record `transport:<host-id>` with the payload `{schema: 1, transport: ...}` (`sync/transports.rs`), the envelope tunnel rules use. In a library that uses central sync (`transports::central_library`: this device has cut over and keeps the library's rows in its account) the route is the library's. `transports::set` writes a dirty `transport:` row of the account under the tunnel rules' write gate, and the capture publishes it in the Catalog's `transports` field (`sync/central/projection_local.rs`, `sync/central/payload.rs`): a `Vec<HostTransport>` declared like `tunnels`, omitted when empty so that a library without routes serializes as it always did and stays readable by every release, with at most one route per host, at most 256 (`MAX_ROUTES`), each passing `HostTransport::validate` with `pam.justification` null. The initial and delta projections (`sync/central/projection_cache.rs`, `sync/central/projection_delta.rs`) rebuild the rows from the Catalog, and `transports::get` and `view` read the account row when there is one, else the `local.transports` entry. The Catalog is one sync record of at most `MAX_PLAINTEXT_BYTES` (64 KiB) shared with collections, group orders, tunnel rules and saved databases, so every write that changes it (`transports::set`, tunnel saves, database saves, MCP `set_transport`, the adoption merge) builds the candidate Catalog and is refused when it would not fit, with the "This library has no room for more routes, tunnels or databases" sentence (`NO_ROOM`); removing a route, a tunnel or a database is never checked. What a grant request taught the device, the last justification and length, is not part of the route: it is the device-local `LocalState.transport_grants` (`GrantMemory`), so requesting a grant never edits the synced library. Local state version **10** (`TRANSPORT_SYNC_STATE_VERSION`) is raised by synced route rows or by that grant memory, and a 1.12 build refuses to open it; version **9** (`TRANSPORT_STATE_VERSION`) still covers device-local routes, and an initial projection that keeps a device's routes is written at 10 as well. Routes saved before central sync stay in `local.transports` through first publication and adoption (`sync/central/initial_projection.rs`, `keep_routes`; adoption re-keys them with the hosts' new ids, `transports::follow_hosts`), and one publish step moves them into the library. No capture takes them (`catalog_of` reads the account's rows only): before its capture, the central dispatch's prepare (`sync/central/active_dispatch.rs`, `publish_local_routes`) makes each one whose host the library has, and that the library holds no row for, a library row (`transports::publish_local`, through `write_library`), with an ordinary save of its own. It walks them in host-id order while the Catalog fits (`transports::local_routes`): a route whose host is missing is passed over, and the first route that does not fit stops the walk, so it and the rest stay local, which the Google Cloud page says (`TransportSyncView.reason`, `no_room`). The step waits while the library's latest Catalog, staged by the pull, is not yet read into this device's rows, which the delta projection at the end of that round does, and while the Catalog is in conflict (`projection_capture::catalog_settled`): moving routes in then would hold the Catalog against an older basis and raise a conflict. A library whose writes are blocked, or that is frozen for an encrypted migration, takes none. Two devices that change the Catalog inside one pull-to-push window meet in a Catalog conflict, which merges item by item (`sync/central/catalog_merge.rs`): against the version this device's change was made on, a tunnel or a database by its id, a route by its host, a collection by its id and a group order by its scope take the side that changed them. The dispatch's prepare merges a conflict without collisions before the publish step (`sync/central/active_dispatch.rs`, `merge_catalog`; `sync/central/catalog_conflict.rs`): it reads the merged Catalog into the rows and replaces the Catalog's draft with it, confirmed on the library's version, keeps this device's new routes while they fit and leaves the rest on this device, and waits, with a sentence, when the result still does not fit. Items both devices changed differently wait for Central conflicts, whose Catalog row lists them and settles them for one side (`CatalogConflict.tsx`). A push the relay refuses for a stale revision (409 `revision_conflict`) makes the round pull again, up to three times (`sync/central/active_cycle.rs`), and a record in conflict keeps its 16 latest entries (`replica::keep_latest`). Chain-mode and account-less libraries keep routes in `local.transports` only. Leaving a chain-mode account (`sync/record_leave.rs`) keeps the routes of the hosts that stay as local ones (`transports::preserve_on_leave`); a library that uses central sync has no leave path yet, so a later one must call it with the state from before the account's rows are dropped.

Account actions and PAM on its own. `gcp/cli.rs` is the one place Lunport runs gcloud: `locate` looks on `PATH`, in the installers' places, then asks `$SHELL -i -l -c 'command -v gcloud'` once (5 s), and caches the answer for the run; `run` spawns it with an argument list through `crate::process`, stdin closed, `CLOUDSDK_CORE_DISABLE_PROMPTS=1`, one run at a time, killed past its bound or on cancel, stderr streamed line by line (the sign-in page's address goes to the window as `gcp://sign-in-url`). `session/gcloud.rs` holds the four account actions (`AccountAction`: `auth login <a> --force --no-activate`, `auth login --no-activate`, `config set account`, `auth revoke`), each account checked with `transports::is_email` before gcloud starts, and `TokenSource::forget` drops cached tokens after each. `session/pam.rs` is the Access tab: `gcp_pam_overview` searches entitlements (`GcpClient::search_entitlements`, `callerAccessType=GRANT_REQUESTER`, `callerAccessType=1` in mocks) in the routes' projects and the added scopes, adds the entitlements routes name, reads each one's grants, four calls at a time and none started after 60 s; `gcp_pam_request` requests on an entitlement it lists, by full name, and does not wait for an approver (`pam::request_and_wait` with `approver`). `GcpClient`'s grant calls take an entitlement's full name (`pam::EntitlementName`), so folder and organization entitlements go the same way. Search scopes and the grant memory (one per entitlement, its record id the first 16 hex digits of the SHA-256 of its name) are `Meta` records `pam_scope:<id>` and `pam_request:<id>` (`sync/pam_records.rs`): account rows in a central library, published in the Catalog's `pam_scopes` and `pam_requests` (at most 64 and 32, omitted when empty, rebuilt by both projections like tunnels), `local.pam_records` otherwise, moved in by the same publish step as routes. A memory collision in a Catalog merge takes the synced version without review, a scope collision is reviewed, and a merge too large drops memories first. Local state version **11** (`PAM_STATE_VERSION`) is raised by any of these records, local or the library's; the delta save that brings the first ones is admitted like the routes' raise (`record_runtime`). The connect gate reads the entitlement's memory first, then the host's from `local.transport_grants`, which requests empty as they go.

Validation without Google: `gcp::testing::FakeRelay` speaks the relay subprotocol in front of a TCP target and can refuse, close with a code, cut the socket or stall; `cargo test --locked --lib -- gcp:: ssh::engine_tests::iap` runs the codec, credential, tunnel and engine tests (the engine ones use the scratch sshd), `session::record_directory::tests::gcp_transport` the OS Login and PAM decisions with a scripted client, `session::connect::tests` and `session::grants` the grant question, the gate and the IAP grace with fakes, `session::transports` the commands behind a host's details and gcloud's accounts (grant state and requests, and the probe over `FakeRelay`), `session::pam` the Access tab's overview, `gcp::cli` and `session::gcloud` finding and running gcloud with fake scripts, `sync::pam_records` the scopes and grant memory, `sync::transports` the route records, their room in the Catalog and the grant memory, and `sync::central::projection_local`, `sync::central::projection_delta` and `sync::central::adoption` the Catalog's routes, both projections and the move of a device's routes into the library. `pnpm exec vitest run src/components/records/google-cloud.test.tsx src/components/records/connect-via.test.tsx src/components/records/markup.test.tsx src/components/records/trust-and-probe.test.tsx src/components/AuthenticationWindow.test.tsx` runs the Google Cloud page (`GoogleCloudPanel.tsx`), the editor's Connect via (`IapRouteFields.tsx`), a host's card and details, Check through IAP and the grant request (`GrantRequestDialog.tsx`), and the Request-a-grant form. The interface preview shows the Google Cloud page, the host editor's Connect via, and the cards and details, with fakes of these commands in their real shapes: `pnpm exec vite`, then `http://localhost:1420/dev-preview.html?scenario=iap`. The live check against a real jump box is manual.

## Cloud SQL databases

A saved database is a Cloud SQL for PostgreSQL instance that Lunport offers to the apps on this computer on a loopback port, signed in as the person's Google account. Phase 1 is PostgreSQL, the instance's public IP and IAM database sign-in only: a request for a password from Cloud SQL ends the connection with a sentence, and Lunport never sends one. Connecting runs neither gcloud nor `cloud-sql-proxy`; the connector protocol is the one of Google's Go connector, over the token source that already serves IAP and PAM, and the feature builds on the PAM records and the grant memory described above. `gcp/cloudsql.rs` is the Cloud SQL Admin API (`sqladmin.googleapis.com`, v1) behind the `SqlAdmin` trait, so the code above it can script the answers (`RestSqlAdmin` in production, mockito in `gcp/cloudsql_tests.rs`). `connectSettings` gives the instance's `PRIMARY` address, the PEM of `serverCaCert` (which can hold several certificates) and the DNS name the server certificate is made out to: the first `dnsNames` entry, else the legacy `dnsName`, without its trailing dot. `generateEphemeralCert` is sent the public half of a new 2048-bit RSA `EphemeralKey` and the account's access token, and the certificate it signs is the connection's identity; its `expires_at` is the earlier of its own expiry and the token's end, since the instance signs nobody in with it once the token has ended. `list_instances` reads a project's instances for the New database dialog (ten pages at most, `POSTGRES_` versions only, IAM sign-in read from the `cloudsql.iam_authentication` flag being `on`). `AppState.sqladmin` signs with `AppState.gcp`'s token source, so a database and the Google Cloud page share one token cache. Calls block (a caller uses `spawn_blocking`), end at the 20 s `HTTP_TIMEOUT`, never follow a redirect (`generateEphemeralCert` carries the token in its body) and fail as `GcpError` sentences: `Refused` for a `404` ("Cloud SQL has no instance …"), for a `400` with the API's own words (one line, 256 characters, the token blanked) and for the `403` whose details say `SERVICE_DISABLED` ("The Cloud SQL Admin API is not enabled in {project}. Enable it in the Google Cloud console, then try again."), `Denied` for every other `401` or `403`. `Token` carries `expires_at`, and `gcp/auth.rs` serves a cached token only while both the monotonic and the wall clock put its end more than `REFRESH_MARGIN` (5 minutes) away, so a Mac that slept through a token's end does not serve it. The key, the certificate and the token print as `<redacted>`, and the parser's own words are never repeated for a certificate, which carries the token.

`gcp/cloudsql_tls.rs` dials the instance as the Go connector does: TCP to port 3307 (`PORT`) within 10 s and the handshake within 10 s more, TLS 1.3 only, with the aws-lc-rs provider named in `ClientConfig::builder_with_provider` (this build has both of rustls's providers), the ephemeral certificate and key as the client identity (`EphemeralClientCert`, whose `Debug` leaves the certificate out), no ALPN, no metadata exchange and session resumption off (`Resumption::disabled()`: the token rides in the client certificate, so every connection shows the certificate it was given). PostgreSQL then runs inside the TLS with no SSLRequest of its own. The server certificate must chain to any one of the certificates of `serverCaCert` (`InstanceVerifier` trusts all of them, as an instance whose CA hierarchy holds several sends them all) and be made out to the instance's DNS name in its SAN; with no usable DNS name the server name is `cloudsql.invalid`, which no certificate names. A certificate whose chain verified and whose one fault is its name still passes when its subject common name is exactly `project:instance`, which is how legacy instances name theirs (`x509-cert` reads the common name), and every other verdict stands as webpki gave it. In TLS 1.3 the client finishes its handshake before the server has checked the client certificate, so a refused certificate shows only at the first read or write. The module's tests perform real handshakes against authorities and certificates made when they run.

A saved database is a `Meta` record `database:<16-hex-id>` with the payload `{schema: 1, database: ...}` (`sync/databases.rs`), the envelope tunnel rules use, stored as search scopes and grant memory are (`sync/pam_records.rs`). It names the instance (`project`, `region`, `instance`), the `environment`, the Google `account` (none: gcloud's active one), the `default_database`, an optional `pam` check of the type routes use and the `local_port`, which syncs with the rest: the port a person chose is the library's, whether a port runs is per device and never syncs (`DatabaseLive`); `engine` and `network` have one value each so far. In a library that uses central sync (`transports::central_library`) it is the library's: `databases::set` compares `expected` with what `view` reads, refuses a new database past `MAX_DATABASES` (256) and a library whose writes are blocked, writes a dirty `database:` row of the account and checks that the Catalog still fits (`transports::ensure_room`, `NO_ROOM`), and the capture publishes it in the Catalog's `databases` field (`sync/central/projection_local.rs`, `sync/central/payload.rs`): a `Vec<SavedDatabase>` declared like `tunnels`, omitted when empty so that a library without a database serializes as it always did, each passing `SavedDatabase::validate`, ids unique, with `pam.justification` null. A database never stores a justification: `PamCheck` has the field for the routes earlier releases saved, `payload_of` clears it from every write, and `valid_catalog` refuses a Catalog that carries one, when it is built and when it is read. What a request taught Lunport, the justification and the length asked for, goes to the entitlement's grant memory (`pam_records::remember`, the one a host's request writes too), not to the database. `Catalog` is `deny_unknown_fields`, so an older release refuses a Catalog that holds `databases`: devices on older releases stop syncing such a library, which is the compatibility sentence of the user guide. The initial and delta projections rebuild the rows from the Catalog (`databases::catalog_rows`), and a Catalog merge treats a database as it treats a tunnel: item by item by its id, a difference both devices made waits for Central conflicts (`Collision::Database`, `Over::Databases` when the merged Catalog holds more than 256). With no account, or the older chain-mode account, a database stays in `local.databases`, and the publish step that moves a device's routes into the library moves it too, as its third part (`projection_capture::move_local_routes` runs `transports::publish_local`, `pam_records::publish_local` and then `databases::publish_local`), one database at a time while the library has room; a first publication, an adoption and a replacement keep every database as the device's own for that step (`databases::preserve_on_leave`, which no host id remaps, since none names a host). Local state version **12** (`DATABASE_STATE_VERSION`, after the **11** above) is raised by any saved database, the library's rows (tombstones included) or the device's own, and by an initial projection that keeps one; `validate_state` refuses a `database:` row in a state below it, and an older build refuses to open it.

What a connection needs from Google is `session/database_access.rs` and `session/database_upstream.rs`, over the steps `session/grants.rs` shares between hosts and databases: `current_grant` (the first entitlement of the check that holds a grant in flight, how fresh it is and when it ends), `ask_and_request` (the Request-a-grant question, five minutes), `request_active_grant` (request, or take the one in flight, and read it back every `POLL_EVERY`, 2 s, for `ACTIVE_WITHIN`, 60 s), `pause` and `Grace` (120 s in steps of 10 s), and `GrantGates::obtain`. A database's `GateKey::new` is the very key `GateKey::of` gives a host whose route names the same account, project, location and entitlement, so the two ask the person once, and a request from the Databases page (`databases_request_grant`) takes the same gate. `fetch_material` asks for the connect settings, refuses an instance without a public IP, makes a new key and asks for a certificate for it. It tries a `403` again, and only a `403` (a `401` is the token's, which no grant explains), every `Grace::step` until `Grace::span` has passed since the first refusal, when the grant it relies on was given within two minutes: Google applies a new grant late. The database user is the certificate's account (`iam_user`: the email, and for a service account the email without `.gserviceaccount.com`). `CloudSqlUpstream` is the `Upstream` the ports use. It keeps a grant check for `GRANT_RECHECK` (5 minutes) at most and never past the grant's end, and the material (the TLS configuration, the address and the user, numbered by a generation) until `REFRESH_AHEAD`, 4 minutes, before its certificate stops being useful. The certificate's end is capped at its token's, so a renewal normally finds the cached access token inside the token source's 5-minute margin too, and reads gcloud's credential files again: a new `gcloud auth login` needs no restart. A database saved without an account signs in as gcloud's active account, read for every connection (`gcp::auth::active_account`). The material is dropped by a failed dial (`forget`, for the generation that failed only: in TLS 1.3 a refused certificate shows only after the handshake), by a changed account (`Kept::keep_for`; so does a certificate for another account than the last one although the database names the same, the credentials having changed under it, and the grant is then checked once more before the certificate is used), by a grant that ended, and by a stop or a delete (`release`).

The local port is `session/database_ports.rs`. `DatabasePorts` (`SessionRuntime::databases`) runs every port on one small runtime of its own (two workers named with `identity::thread_name("database")`); each port is registered with the broker (`register_tunnel`) while it runs, so that quitting stops it. It refuses a 17th database (`MAX_RUNNING_DATABASES`) and a connection past `MAX_PORT_CONNECTIONS` (64, a cancel request counted), and a port keeps the database as it was saved when it started: `DatabasePorts::edit` refuses a change to a running one, and one edit lock keeps a save from coming between a start and the read it starts from. A port listens on 127.0.0.1 only. A program that listens on every address (Docker's `-p`) does not make the bind fail on macOS, yet it would answer apps that dial `localhost` over IPv6, so `listen` first probes 127.0.0.1 and ::1 (300 ms each) and fails with "Port 6543 is already in use on this computer." The port's password is 24 random bytes (`getrandom`) as URL-safe base64 without padding, 32 characters, kept in the keychain account `database:port-password:<id>` (`password_account`, through the `Keychain` trait and `crate::secrets`). `replace_password` stores it before it is answered, so a keychain that cannot keep it leaves the old one in force; `Port::set_password` gives a running port the new one for the connections that come from then on; `forget_password` wipes it when the port stops; and a delete removes the account (`delete_database`). It never enters a sync record, a log, an error sentence or an event.

An app's start-up is `session/pgwire.rs`, which reads only the message it was asked for. `read_first` reads the first message of a connection: an SSLRequest or a GSSENCRequest, which the port answers `N`, at most twice (`MAX_ENCRYPTION_REQUESTS`, since libpq asks for both, one after the other); a CancelRequest of 16 to 268 bytes, passed to Cloud SQL as it came with the certificate the database's connections have now (`Upstream::connect(db_id, None)`); or a protocol 3 start-up message of at most `MAX_STARTUP_BYTES` (10,240). Anything else, or a third request for encryption, ends the connection with a sentence. `Startup::negotiated` answers an app that asks for a minor version above 0, or sends `_pq_.` protocol options, with a NegotiateProtocolVersion message (protocol 3.0, the options in the order sent) ahead of the password request, and passes 3.0 without them on. The port then asks for a cleartext password, which crosses loopback only, within `SIGN_IN_WITHIN` (30 s) of the connection (`auth_cleartext`, `read_password`, at most `MAX_PASSWORD_BYTES`, 1,024) and compares it with the port's in constant time (`passwords_match`, the `subtle` crate; only a difference of length is told at once, and the generated password has a fixed length). Only then does it call `Upstream::prepare` on a blocking thread, since a grant question can wait for the person, decide whether the session carries the lock (`Port::register`: a prod database with no open writable window) and rewrite the start-up message. `with_user` puts the IAM user in the place of the first `user`, whatever the app sent; for a locked session `with_read_only_lock` appends `-c cloudsql_session_read_only=locked` to every `options` parameter, adding one when there is none, and removes any other parameter named `cloudsql_session_read_only` in any letter case, because PostgreSQL takes the switches of the last `options` only and applies every other parameter after them. A message of more than 10,000 bytes after its length word (`MAX_CLOUD_SQL_STARTUP_BYTES`; Cloud SQL closes the connection without a word on a longer one) is refused on the spot with "The connection settings are too long for Cloud SQL. Remove some options and connect again." `read_server_auth` reads Cloud SQL's first answer within 30 s: an acceptance or an error goes to the app as it came, and a request for any password becomes "Cloud SQL asked for a database password. Turn on IAM database authentication for {connection}." Every other refusal is a FATAL ErrorResponse with an SQLSTATE and a printable sentence of at most 512 characters (`28P01` wrong password, `28000` a connection that could not be prepared or that Cloud SQL asked a password of, `08006` Cloud SQL not reached, `08P01` what no app sends or a start-up too long for Cloud SQL, `53300` a full port), and the session is then relayed byte for byte.

The write lock is per port. `WRITABLE_WINDOW` (15 minutes) opens when `databases_unlock_writes` succeeds. On a Mac that can ask, `os_auth.rs` calls `os_auth.m`, which evaluates `LAPolicyDeviceOwnerAuthentication` through LocalAuthentication on a blocking thread and waits 120 s for the person; a refusal, a cancel and no answer are all `Ok(false)`, and the unlock answers `STAY_LOCKED`. `os_unlock_method` tells the page how this computer confirms (`UnlockMethod::System` or `Dialog`), and where the system asks, the page's own `confirmed_in_app` does not count. A session's lock is decided when it registers and kept for as long as it lasts: sessions open when the window opens keep their lock, and `reconnect_locked` closes the idle ones so that their apps connect again. Whether a session is idle comes from Cloud SQL's side. `ReadyTracker` follows the stream's framing (a type byte and a four-byte length) with a few bytes of state and never a message, and `Flow::idle` holds when the stream is between messages after a ReadyForQuery with status `I` (outside a transaction), the app has everything Cloud SQL sent, and the app has sent nothing since (the idle ReadyForQuery messages are counted against what the app sent). When the window ends (`lock`, or the port's one-second `TICK`), a session that came without the lock closes as soon as it is idle and no later than `CLOSE_UNLOCKED_WITHIN` (10 minutes) after the window ended, which rolls back what it still has open, and a window opened again before then reprieves it. The window and that deadline end when either the wall clock or the monotonic clock reaches them (`Moment`, `Clocks`), so a wall clock set back does not stretch them and a Mac that slept through them ends them as it wakes. Stopping a port ends its window, and the next start is locked.

`DatabasesPanel.tsx` is the Databases page (`LibraryNavigation.tsx` lists it after Tunnels), reading `databases_list` every 1.5 s; `DatabaseEditor.tsx` is the New database dialog, `DatabaseAccessCard.tsx` the connection details and the write lock, `DatabaseBadges.tsx` the environment badge, and `src/lib/databases.ts` the commands and helpers such as `suggestPort` (from 6543) and `connectionUrl`. The commands are in `session/databases.rs` (`databases_list`, `databases_save`, `databases_delete`, `databases_start`, `databases_stop`, `databases_port_password`, `databases_rotate_port_password`, `databases_unlock_writes`, `databases_lock_writes`, `databases_reconnect_locked`, `databases_pam_status`, `databases_request_grant` and `databases_list_instances`, with `os_unlock_method` in `os_auth.rs`), registered in `lib.rs`, each checking `main_only`, and `src/lib/ipc-parity.test.ts` holds them to the frontend. A database that runs here although its record is gone is listed with `removed` set, so that it can be stopped.

Validation without Google: `cargo test --locked --lib -- gcp::cloudsql sync::databases session::pgwire session::grants session::database os_auth` runs the Admin API client against mockito, the TLS handshakes, the record storage with its room in the Catalog and its publish step, the start-up codec, the grant steps, the material cache, and the ports over real loopback sockets with a fake `Upstream` standing for Cloud SQL and clocks the tests move themselves. `sync::central::payload`, `sync::central::catalog_merge`, `sync::central::projection_local`, `sync::central::projection_delta`, `sync::central::initial_projection`, `sync::central::adoption` and `sync::central::device_tests::active_cycle_tests` cover the Catalog's field, both projections, the merge and the move of a device's databases into the library. `pnpm exec vitest run src/lib/databases.test.ts src/components/records/DatabasesPanel.test.tsx src/components/records/DatabaseEditor.test.tsx src/components/records/DatabaseAccessCard.test.tsx` runs the page. The live check against a real instance is manual.

## Embedded SSH terminal

Choose **Lunport (in app)** in **Settings → Connections** or the Records connection menu. The choice, terminal text size and cursor preference persist locally through the existing settings store and settings export/import. New installations default to the app terminal; existing terminal preferences are preserved. Records connections use stable host IDs and Legacy connections use saved aliases through the same broker. Unsupported Legacy directives are refused by the existing adapter; Development still refuses external OpenSSH evaluation.

Double-click a ready host or use Quick connect. Library and session tabs stay mounted when switching. Tab metadata is transient; raw data, credentials and live handles never enter persistent settings. Closing a running/connecting tab asks before ending its session; ended tabs close immediately. The workspace supports up to eight tabs, adjacent-tab selection on close, Ctrl+Tab switching, terminal Find and text-size shortcuts. A workspace reload revokes pending opens before ending its existing sessions.

The renderer is `@wterm/dom` with `@wterm/ghostty`, both pinned to 0.5.4. Vite bundles the Ghostty WASM asset locally, including in release builds; no external terminal, WebSocket server, Bun or Zig toolchain is needed. Rust connects to the existing protocol-1 broker, preserving the SSH engine, native password/passphrase prompts, host-key verification, jump hosts and quit lifecycle. The WebView receives ordered binary packets through a Tauri channel, with a 256 KiB acknowledged output window and bounded input. Raw terminal bytes and keystrokes never enter React state or application logs. Remote clipboard writes and image storage are disabled. App appearance updates terminal colors without reconnecting.

For a disposable real SSH target on macOS or Linux:

```bash
python3 scripts/preview-ssh.py
```

Keep that process running. It prints a loopback port, a temporary SSH config and a throwaway private key. Import the printed config into **Lunport Dev**, explicitly select its optional key copy, then double-click `terminal-preview`. Verify the host fingerprint against the printed fingerprint. The remote shell uses an empty temporary HOME. Ctrl-C stops the fixture and its sessions, then removes its files; its imported host/key can be removed from the Development library afterward. Production data is not involved.

Validation: `pnpm test` includes terminal transport ordering, binary data, input limits and cancellation races. `cargo test --locked --lib session::embedded::tests` includes a real scratch OpenSSH shell, ANSI/Unicode output, remote PTY resize, exit status and cleanup, using only disposable keys, for both ID and alias queries. The SSH engine's existing bounded overflow notice still applies if a producer outruns the renderer; the preview does not claim lossless output under sustained overload. Splits and remote process restoration are not implemented; reconnect starts a new shell.

## Brand assets and compatibility

The mark geometry lives in [lunport-mark.json](../src/brand/lunport-mark.json); [product.json](../src/brand/product.json) supplies the About copy. Regenerate native and web icons from the canonical geometry with:

```bash
node scripts/generate-brand-icons.mjs
```

Use Lunport for visible product copy and `ysya/lunport` for current repository links. Identity values are written once: the identifier, product name, main binary and publisher in the Tauri configurations (`src-tauri/tauri.conf.json`, `src-tauri/tauri.dev.conf.json`), everything else the operating system sees (credential services, login items, installer identities, the console helper, pipe and thread prefixes, the macOS helper identifier) in `src-tauri/src/identity.rs`, whose tests compare it with the configurations. Rust reads them from `identity`; scripts and workflows read the configurations, or `scripts/identity.mjs`, which prints each profile's identifier, product name, publisher, main binary, console helper, credential service, login item and installer identity, and the manifests of the frozen macOS executables. It reads the values the configurations do not hold from the `PRODUCTION` and `DEVELOPMENT` blocks and `HELPER_V2_IDENTIFIER` in `identity.rs`, each written as a plain string literal, which `scripts/identity.test-node.mjs` checks. Names from before 2.0 appear only in the `legacy_identity` (Rust) and `legacy-identity` (TypeScript) modules, in `scripts/legacy-identity.json` for scripts and in the other places `scripts/identity-guard.mjs` lists; the Policy job fails on any other. A value that can never change, such as a key-derivation input or a folder already on users' disks, stays where it is with a `frozen-identity:` comment that says why. See [installer identity](../src-tauri/installers/README.md) before changing a value the installers register. Published releases, validation records and signatures keep their names.

The macOS pre-runtime migration in `macos_install.rs` renames only the running legacy app bundle, preserves its parent and leaves a relative compatibility symlink. It uses no-overwrite moves, a bounded installation lock and a recovery journal. Permission repair elevates the system interpreter with a fixed Foundation file-operation program and literal validated paths. It does not execute the mutable application binary as root, start Tauri or read user credentials. Development can exercise migration only inside its existing write sandbox. Login repair changes only an existing launch-at-login entry under the earlier name whose old command resolves to this installation.

MCP client setup in `mcp_setup.rs` uses the existing stdio adapter and grants no host access. Codex TOML edits preserve comments; Claude JSON edits preserve unrelated values. Existing files are backed up with owner-only permissions, managed symlinks are refused and concurrent changes are checked before replacement. Cursor/VS Code URLs are generated in Rust from a fixed client enum and this installation's command; the WebView receives no new filesystem or general execution capability. Development writes client fixtures only under its sandbox home and does not open external install links. Linux AppImage setup records the persistent AppImage path rather than its temporary inner executable.

The 2.11.2 runtime has a narrow [context ownership patch](../src-tauri/vendor/tauri-runtime-wry/LUNPORT_PATCH.md). Preserve its provenance and run the handle-only, native tray and actual GUI regressions before updating or removing it. The patch keeps worker handle clones from copying a non-atomic native event-loop reference count.

## Central account builds

Central sync is enabled in normal macOS, Windows and Linux desktop builds through the default `central-sync` feature. Windows uses pinned native filesystem handles, owner-only ACLs, bounded source capture and write-through atomic publication; Unix permission tests remain platform-specific while migration and synchronization fixtures run on every supported platform. A build can embed a sync service with the build-time variable `LUNPORT_RELAY_URL`: fresh account setup uses that HTTPS service while an existing pinned account keeps its original service. Release CI sets it empty, so public installers start with a blank server URL; self-hosted builds may leave it unset and enter a service in Sync. A debug build without it uses a local `wrangler dev` at `http://127.0.0.1:8787`.

The ordinary-library `app_profile_build` integration test checks the shipped capability outside `cfg(test)`. Central tests use isolated in-memory credentials; never run credential-service tests against a real user Keychain as a general release check.

## Release workflow

Stable releases use release-please. A push to `main` opens or updates a release PR; merging that PR creates the version tag and GitHub Release, then builds the platform installers and updater assets. Review the version, changelog and checks before merging a release PR. An ordinary feature or documentation merge does not itself publish an installer.

For each release, check the README, user guide and installer names against the actual packages and verify both update channels. Published releases and their assets remain intact. Native runtime changes require a failing baseline reproduction, repaired regression checks and full platform validation before publication.

For a beta, run **publish beta** in GitHub Actions with a new `X.Y.Z-N` version, using a numeric suffix. The workflow stamps the version, creates the prerelease, builds the platforms and updates the `updater-beta` manifest. Beta-channel devices can receive Stable releases too.

If a build fails, use **Re-run failed jobs** on that run to keep the same source and inputs. Do not use `build-platform.yml` for a beta: it does not stamp the beta version or update that channel. Use a new version for changed release content; preserve published tags, installers and signatures.

The **update beta channel** workflow can reconcile the Beta manifest with an existing release. It checks that the release manifest is complete, never moves the channel backwards and leaves an already current channel alone.

Before promoting a release, the channel script maps updater URLs to that release's public download assets and updates its `latest.json` if needed. GitHub REST asset URLs consume an [unauthenticated API quota](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api) and can return HTTP 403. This metadata repair preserves versions, platform aliases, installer bytes and signatures; it does not require rebuilding or retagging a release.

The Windows bundle workflow separately validates helper placement and old-version installer upgrades. It supports verified candidate reuse for installer-only diagnostics; see [installer documentation](../src-tauri/installers/README.md). These unsigned CI artifacts are not published releases.
