## 2. Groups: model and precedence

Use a `group` record kind in a space; Local has its own groups map. A Group has a stable random 16-hex ID, scope, revision, schema 1, a trimmed name (1..128 characters, reject controls), optional parent ID and optional defaults. IDs, parent links and host membership always refer to stable identities. A group cannot cross Local/Space boundaries by reparenting.

`GroupDefaults` contains optional `port`, `user`, `authentication`, `jump`, `keepalive_secs`, `keepalive_max_missed` and `connect_timeout_secs`. `authentication` is one atomic object `{auth: key|password|interactive, key_id: string|null}`; a key authentication default requires a valid key ID. Group defaults contain no password, passphrase, private key, hostname or host-key pin.

Host schema 3 adds `group_id: string|null` and `inherit: InheritedField[]`. Supported inherited fields are `port`, `user`, `authentication`, `jump`, `keepalive_secs`, `keepalive_max_missed`, `connect_timeout_secs`. Schema 2 hosts remain supported and must have neither a group nor nonempty inheritance. Empty extension fields are omitted when serializing schema 2. Existing hosts keep their explicit settings unless a user chooses inheritance. Hostnames, aliases, notes, tags and pins are always host-owned.

For an inherited field, the nearest ancestor Group with that default wins; otherwise use the app default (port 22, OS username, password authentication with no key ID, no jumps, keepalive 30 seconds/3 misses, connect timeout 15 seconds). A field outside `inherit` uses the host's explicit value. A Group with no value inherits its parent's value. Authentication and key ID resolve together. Return the effective payload plus an `inherited_from` mapping keyed by inherited field to Group ID, or `default` for app defaults. Editors retain raw values separately.

Resolution validates a bounded ancestor path (maximum 32 Groups), same scope, existence, no cycles and no opaque winning ancestor. Local creation/update rejects invalid parents, same-parent duplicate names, invalid defaults and invalid resulting routes. Concurrent remote errors remain inspectable: affected hosts become Needs review and cannot connect. Never silently use a missing Group's host fallback for fields marked inherited. Unknown or newer winning group records must shadow stale caches just as host records do. Tags remain independent filters.

Repository snapshots retain raw host records and add effective payload, inheritance provenance and group diagnostics. Readiness and jump routing use effective values. `resolve_host_chain` and the Records directory must feed these same values to CLI, MCP and deployment. Endpoint checks and host-key pin CAS compare effective hostname/port. Any Group change/reparent that changes an affected host's effective port clears that host's pin in the same persisted candidate. New connections may not reuse a pin from another endpoint.

Group CRUD uses optimistic revisions and the existing SyncCore lock/persist/replace/generation discipline. Deleting a group removes its subtree but preserves all affected hosts: materialize their current effective settings, detach membership/inheritance, preserve IDs/credentials, and tombstone the Groups atomically. The UI confirms descendant/host counts. Moving a host between scopes materializes effective values and clears Group membership; it must not retain a dangling Group from the old scope. Reparenting stays within one scope. Changing Group defaults displays the affected-host consequence before save.

## 3. Formats, synchronization and lifecycle

Keep old ungrouped state version 3 readable. Add state version 4 for Group-capable storage, accepting both versions explicitly; future version 5 or higher remains blocked without changing source bytes. Version 4 protects against older clients rewriting Group data. Before the first local promotion from 3, save a mode-0600 backup of the source state (named with its digest), then atomically publish the new version. Expose the required promotion in overview/UI and require a confirmation that other clients are updated before the first Group or first inheritance use. Host create/update gain a backward-compatible optional `upgrade_confirmed` argument (missing means false), so an Ungrouped host can inherit app defaults without creating a throwaway Group. Schema-2 operations require no promotion confirmation. No upgrade of real user data is exercised by the agent.

Account schemas 3 and 4 are compatible for this client; schema 4 is required before publishing shared Groups or grouped hosts. New ungrouped accounts may stay on schema 3. Promote authoritative account metadata to 4 with a monotonic ordering tuple when shared Groups are enabled; the existing account-before-space push ordering must ensure the schema gate is durably acknowledged before Group/host-schema-3 rows upload. A failed gate publication leaves retryable public state and cannot release child writes. Older clients must be stopped or upgraded when confirming this promotion; do not pretend a schema marker recalls another client's in-flight request. Keep the minimum supported Records account schema at 3 rather than equating it with the maximum.

Groups use the same encrypted envelope/LWW/tombstone rules as hosts. Parse and validate the new kind in record merging, including authenticated identity binding and future/opaque shadow protections. Preserve unknown envelopes and dirty data on partial pulls. Add Group records to rotation, selected-space pulls and round trips. Leaving a chain must preserve Group structure and resolved connection behavior with fresh Local IDs and remapped group-parent/host-membership/jump references; recovery journals stay backward compatible. If a selected source contains unreadable Groups, fail preservation explicitly rather than discarding inherited settings. Legacy v1/v2 migrations produce supported ungrouped hosts; no plaintext secret is introduced into any state/journal.

The relay accepts lowercase kind strings generically (`relay/src/index.ts:350`); no relay protocol or deployment change is necessary. Use fake relays and two-device tests to prove Group convergence and lifecycle preservation, rather than relying on this observation alone.

## 5. Records MCP: transport and tools

Implement the approved section-8 model: the stdio adapter has no credentials and calls the OS-authenticated session IPC (Unix socket or Windows named pipe), without a TCP/token/runtime-file dependency in Records mode. Preserve Legacy functionality in its existing mode during the transition. The broker must distinguish Connect and MCP clients, refuse unsupported protocol versions, and never accept client-reported PID/process names as trusted requester identity. A versioned IPC extension may carry metadata calls and exec; document actual messages and compatibility in the implementation ledger. Old `run` in Records reports `run was renamed to ssh_exec`; do not silently grant new execution via an old name.

Records tools: `list_hosts`, `get_host` and `ssh_exec`. Stable host IDs are preferred; exact aliases are accepted only if unambiguous. Keep `get_effective_config` as a metadata compatibility alias. Metadata contains sanitized host ID, alias, effective hostname/user/port/auth/key ID/jumps/tags/scope and Group path/provenance; exclude private material, passwords, passphrases, imported text, notes and host-key public blobs. Only individually allowed host IDs are exposed. No inherited or alias-based policy grants.

`ssh_exec(alias, command, timeout_seconds)` runs without PTY; the `alias` parameter accepts the preferred stable host ID or an unambiguous exact alias, preserving the approved tool argument name. Timeout is 1..300 seconds (default 60); command maximum is 16,384 UTF-8 bytes and retains the existing control/bidi/display-safety checks. Cap stdout+stderr together at 128 KiB. Return stdout/stderr, ended (`exited`, `signaled`, `timed_out`, `truncated`, `disconnected`, or explicitly `canceled`), nullable exit code and signal, and truncation status. Never invent exit code 0 for missing status. A single request is registered once, and disconnect/JSON-RPC cancellation closes pending authentication and the live exec session. No lifecycle lock is held across approval, connection, authentication, command execution or audit I/O. Revocation/disable must remain responsive.

Policy fields: `enabled`, `allowed_hosts` (stable IDs), `approval_mode: ask|auto_log`, missing mode defaults to `ask`. Ask shows the full command, effective destination, route and requester before execution, expires after 120 seconds and defaults to Deny. Auto-log requires a concrete risk-confirmation dialog before enabling; switching back needs no confirmation. The UI and backend require an explicit acknowledgement for auto-log. In both modes recheck policy and the approved resolved target before connecting and immediately before executing; changes to endpoint, route, auth/key identity or removal cancel the request and require a fresh approval. Group-derived changes are part of this check.

Ask uses the existing host-key confirmation hub and a new native authentication question hub for passphrase/password/keyboard-interactive input. Questions are bounded, tied to their request/hop, honor echo, escape server text, expire/cancel with the request, and hold answers only in zeroizing memory. Auto-log never opens confirmation/auth windows or pins a key: missing pin, locked key, password or 2FA requirements return `needs interaction: <reason>`. Do not reuse globally unlocked key material to evade this rule when an interaction is required.

Trusted requester attribution comes from the IPC peer PID and existing process-chain utilities; missing identity is clearly Unknown. Sanitize self-reported MCP clientInfo name/title/version, each to 100 characters; display it as self-reported alongside process attribution, never as verified identity. Sanitize again in the app, because the IPC client is untrusted.

Persist `<app data>/session-log.jsonl` with the last 1000 entries, mode-0600 atomic writes, public execution metadata only. Include at_ms, client (connect/mcp/deploy), host ID/alias, command (empty for connect), outcome, ended/nullable exit code/signal, mode, requested_by, requester_id, and client_info. Do not log outputs or authentication answers. Loading tolerates a partial trailing line and surfaces corruption/I/O limits without fabricating success. Audit persistence failure must be visible; an execution already completed must not be rerun automatically. AI Access shows the most recent 10 with request attribution. App quit cancels and drains MCP requests as well as interactive sessions.
