## Contracts

- sync_once owns syncing and lifecycle. fresh_account_gate does not reacquire lifecycle: native shared commands hold lifecycle across fresh proof and pure Repo mutation. Full account pull since0 on every proof prevents cursor caches from hiding schema changes. Gate observation uses publication -> core; no doc/vault acquisition or external callbacks under those locks. Local generations cannot invalidate authenticated evidence for the same latest account/relay.
- Non-Compatible account proof durably blocks shared writes and preserves caches/cursors/dirty/sealed; future version stays conservative across later schema3. Pending marker stored explicitly. Failure to persist authenticated denial sets current core.save_blocked with a safe memory gate; restart shared commands still require new fresh account proof. Pending targets with no live account store marker/future max inside the pending operation, because global common gates require a live account. Pending presence itself blocks shared changes.
- Selected spaces use baseline0 then cursor, merge into latest section, retain shape-valid relation conflicts for review and skip publication of that conflicted space. Unselected spaces have no requests; missing spaces are marked and never recreated/deleted automatically. No SSH doc/config, Include, .pub, slots or agent tail. Frozen push retains dirty work and durably remembers FreezeInfo so subsequent rounds poll account only.
- Exact receipts apply to latest matching record/ciphertext even across concurrent local edits. Remote acceptance is kept in memory if its disk receipt save fails; unsaved storage is retried before another credential/network callback. Generation bounds are checked before callbacks and before replacing state. No partial old snapshot replaces current Local metadata.
- Background errors increment retry counters and expose only a fixed diagnostic. Format/pending/save-blocked reasons take precedence; last successful timestamp remains unchanged on failure.
- Account create/join accept device_name inside lifecycle, stage trimmed name with stable device identity and own Device metadata. Schema2 join requires explicit migration before any state/credential/remote write. Schema4/pending/invalid join refuses. New account schema3 and existing compatible join preserve Local records/material.
- PendingAccountOperation carries fixed32hex ID, kind/phase, trimmed device_name, relay URL, strict staged Keychain name sync:records-pending:<id>, prepared public/encrypted account and optional space, plus optional validated migration marker. No mnemonic/token/encryption key/private text in journal. Prepared -> RemoteCreated/Publishing -> ActivationReady -> Activated -> cleanup uses fixed identities; accepted rows persist seq/dirty receipts. Activation keeps the journal until staged-code deletion and final clear succeed, and cleanup repeats fresh gating.
- Generated code is an explicit zeroizing result. A failure after initial durable preparation returns complete=false plus code/error so denial does not strand an unknown generated identity; resume_pending with supplied code verifies the exact fixed chain. Current code promotion failures retain staged credential and journal. No cancellation/rollback/remote-deletion claim.
- create_space durably stores sealed credentials before remote create, establishes baseline0 and publishes metadata; retry uses same space ID/ciphertext. Selection/rename re-authenticate account before staging; metadata revisions use checked logical clocks. Pending operation blocks other shared edits while Local remains usable.
- Explicit key publish validates public/private/fingerprint/passphrase identity and rejects opaque/deleted/conflicting account authority before staging. Secret revision/time advances past the latest private header, including future clocks; only encrypted Key enters state. unpublish only sends an authenticated secret tombstone and preserves public metadata/local material. Download is explicit: fresh account proof -> live typed keyslot -> zeroizing decrypted secret -> vault worker CAS/journal; new vault ID retains old entry/master/passphrase and no old private files are touched.

## Cost and remaining acceptance

A normal round performs one full account pull plus one pull per selected available space. Every dirty chain adds a full account preflight before its batched push (legacy batching caps reused); receipts never advance pull cursors. Gate-compatible proofs currently atomically save even unchanged account cache, so generation/disk writes occur on each proof. Lifecycle holds across network to serialize structural operations; local shared UI operations wait for it. This is a deliberate first implementation cost, not a performance claim.

Account/space lifecycle retries use additional full target-account proofs before publication, activation and credential cleanup. Network/Keychain/state are resumable per step, not atomic together; crashes can require re-pull/idempotent resend. Client-only preflight cannot guarantee atomic relay freeze or cross-chain migration. No real migration/leave/rotation, merge, push, release or app launch happened.

Next focused plans implement required records leave and rotation, then root runs final integrated gates and immutable review. This basic commit does not claim the entire phase1c acceptance is complete.
