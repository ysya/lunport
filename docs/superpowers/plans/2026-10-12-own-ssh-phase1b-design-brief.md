## Rulings (controller, 2026-10-12)

R1. Order: 1b now, before 1c. Reason (scout): 1c on a dev build would migrate the real sync-state.json to schema 3 and make the installed 0.17 and the second computer read-only; 1b touches no user data.
R2. Host source: a `HostDirectory` interface in the broker (lookup by alias or host id → hops with hostname, port, user, auth method, key_id, keepalive/timeouts; the pinned host key; `pin`/`replace pin`; the keychain key for the password). Implementations: a fake for tests, and a TEMPORARY adapter over today's data (the ssh_config model read through config/, read-only; IdentityFile → vault key via the existing slot rules; passwords from the keychain under today's key) — mark it temporary in its module doc; 1c replaces it with host records. Pins in 1b: a small store in app data owned by the adapter (1c moves pins into `host.host_key`); never write ~/.ssh, never read ~/.ssh/known_hosts.
R3. Host-key confirmation window IN 1b (deviation from the original split, scout's recommendation): modelled on agent/prompt.rs's PromptHub and the existing approval window; strings exactly as spec §14 (unknown: title `Is this {alias}?` … buttons `Cancel`, `Trust this key`; changed: title `{alias}'s host key changed` … buttons `Refuse`, `Accept new key`). Flow (spec §10): engine fails fast with HostKeyUnknown/HostKeyMismatch carrying the observed key → the broker asks in the app window → on trust it pins and reconnects automatically; the CLI prints `Waiting for you to confirm {alias}'s host key in SSHelter.` meanwhile (a `question{kind: host_key_notice}` frame or an event — follow §7.1/§7.2). 1d keeps the host editor, "Forget pinned key" and the rest of the pinning UI.
R4. Windows: the CLI (`sshelter connect`) is macOS/Linux in 1b; it must COMPILE on Windows (cfg-gated) and print a clear "not supported on Windows yet" error there; the Windows Connect button keeps today's launch until phase 3 (spec §13/§16: Windows console work is phase 3). The broker/IPC code must compile on Windows (named pipe server exists in ipc/), but its Windows behaviour is not a 1b deliverable.
R5. IPC: the broker listens on `<app data>/ipc/sock` (own lock), coexisting with the agent's socket (scout: nothing listens there today). Frames per §7.1 (u32 length | u8 type | payload; control JSON, data raw). 1b implements the shell subset: hello, open_shell, data, window_change, answer, close → opened, data, question, event, exited. `exec`/`exec_result` and MCP clients are phase 2 (decode them as "not supported yet" errors, do not implement). Requester identification at accept (peer uid → pid → process chain → identify) is reused from ipc/peer.rs and recorded on the session; approvals are phase 2. Broker sessions must not be subject to the IPC server's 300 s read timeout (scout: server.rs:67-70) — idle shells stay open.
R6. Host process start: move ensure_started / spawn locks / host_command out of mcp.rs into a shared module unchanged; `--mcp-host` becomes `--host`, the old flag stays accepted (an update's restart reuses the arguments); the CLI's wait message is exactly `SSHelter did not start within 12 seconds.` (exit 1).
R7. App lifecycle: open sessions keep the app process alive when the window closes (like MCP today); quitting the app ends every session (spec §4); the single-instance hand-over must not orphan sessions (document what happens; a restart ends them).
R8. Auth in the broker: AuthSource::sign → vault (unlock passphrase-protected keys BEFORE connecting, asking through a `question{kind: passphrase}` frame to the CLI owner); AuthSource::password → keychain only, plus: for a password-first host with nothing stored, the broker asks the CLI owner BEFORE connecting (the engine calls password() before opening the connection — no russh spin); for a fallback after a refused key with nothing stored → the engine skips password → AuthFailed → the broker asks the person and reconnects password-first; keep a typed password in memory only for the retries of that one connect (first contact asks twice otherwise); remember a cancelled password prompt for that connect (do not re-ask via keyboard-interactive). AuthSource::interactive → `question{kind: interactive}` frames with `deadline_ms`; a cancelled or overdue prompt abandons (engine drops the connection; spec §11 `Authentication for {alias} was abandoned ({reason}).`). Typed secrets never reach logs, errors, Debug.
R9. Session lifecycle: the IPC connection owns the session; when the CLI goes away the broker closes the shell and the session from a plain thread (never async, never the UI thread); remember the last window size and send it again once the shell is ready (§7.2); `SessionError::Timeout` from a write is not a dead connection; the broker reports `event{disconnected{reason}}` with the engine's reason and `exited{code, signal}` (nullable) and never reports a disconnect as exit 0.
R10. CLI: `sshelter connect <alias>` and `--id <host id>`; `term` from $TERM (default xterm-256color); raw mode via termios (nix `term` feature or libc — whichever keeps Cargo.lock free of new crates; tokio gains the `signal` feature for SIGWINCH); a `question` leaves raw mode, asks on the terminal (no echo when `echo: false`), sends `answer`, re-enters raw mode; `exited` restores the terminal and exits with the code (a signal → 128 + signal number, like a shell; a disconnect → 255, like ssh); the terminal is restored on EVERY exit path including panic. CLI tests: frame codec, the raw-mode guard with a fake termios, the question flow; Windows console work is phase 3.
R11. Connect button / command palette / tray quick connect (macOS/Linux): argv `<SSHelter executable> connect <alias>` instead of `ssh <alias>`; delete the password autofill and the one-shot channel (agent/oneshot.rs) with its frontend listener and the deploy helpers that become dead code — but only what the scout showed is dead after the switch; keep `ssh <alias>` on Windows (R4).
R12. Errors to the user: spec §11 sentences verbatim (they exist in ssh/error.rs Display; the CLI prints them).
R13. Dependencies: no new crate in Cargo.lock (features only); run every cargo command `--offline --locked` except the ONE task that changes Cargo.toml features, which must show the lock diff (expected: none, or tokio's dependency list gaining signal-hook-registry which is already locked) and then lock it.
R14. Tests: unit tests inline as today; broker/CLI tests on FakeEngine + the fake directory; a few end-to-end tests with the real engine against the scratch sshd harness (ssh/testing) through the real IPC socket in a temp dir; never the real ~/.ssh, Keychain (use the existing keychain abstraction's in-memory double) or agent; never launch the app in tests.
R15. Out of scope for 1b: exec over IPC, MCP and approvals (phase 2), the session log (§8.4), the in-app session list (§10), the Windows CLI/console, host records/import/migration (1c), the host editor and "Forget pinned key" (1d).

## Notes carried from plan 1a's reviews (for the broker's design)
- A fallback password typed while the connection is open makes russh spin (measured ~4.2 s CPU per 5 s) — R8 avoids it.
- A slow keyboard-interactive verdict (> keepalive interval) spins russh too — a russh limitation, documented in russh_engine.rs; nothing to do in 1b.
- FakeEngine gaps the 1a reviews noted (disconnect_now hook, richer connect events, our-close default exit): extend the fake only as far as the broker's tests need, in the task that needs it.
- The shell output queue counts payload bytes only; tiny chunks cost more (Task 3 note): coalesce or size the queue in the broker if measurements show it matters.

## Inputs from plan 1a's final whole-branch review (binding for 1b unless a ruling below says otherwise)
Read items 1–12 of "Not for this wave" in docs/superpowers/plans/2026-10-12-own-ssh-phase1a-final-review-fixlist.md. Rulings on them:
R16. (item 1) `AuthFailed` gains a structured signal for "the server offered password and the source had none" (e.g. a `skipped: Vec<AuthMethod>` or `password_wanted` field); a spec §6.1 change the 1b plan makes and records in the spec; R8's fallback flow uses it.
R17. (item 2) On `NoCommonHostKeyAlgorithm` for a hop with a pinned key, the broker reconnects once with `pinned: None` and a policy that answers Mismatch, so the user gets the normal changed-key warning (§14), never an algorithm error for a pinned host.
R18. (item 3) A fake/real parity suite: the same broker-relevant scenarios against FakeEngine and against the real engine on the toy server; fix the fake where it differs (close exit, writes after close, mid-session disconnect hook, password prefetch order, KI deadline, missing password → KI, Timeout/Channel errors) as far as the broker relies on it.
R19. (item 4) Fix ByteQueue's per-chunk overhead (coalesce into the back chunk while it stays under 16 KiB) in 1b, before any beta — a malicious server can otherwise amplify memory ~40×.
R20. (items 5, 6, 10, 11) Decide in 1b and record: the gap notice when output goes quiet; a refused PTY/shell request (add a reason to the ending); server banners (USERAUTH_BANNER) shown to the CLI user (a reasonable-person expectation); a DISCONNECT during the handshake read from the hop's record.
R21. (item 7) Narrow the `ssh` module's public surface to what the broker uses (`pub(crate)`), once it consumes it.
R22. (items 8, 9) The thread/lifetime rules are design inputs (see R9); defer the real channel close until the first byte or ~3 s, so closing a terminal tab right after opening it does not strand a PTY process on a macOS sshd.
(item 12 → plan 1c: host-record validation of absurd timeouts, keepalive_max_missed = 0 warning, empty key_id; show key names, not ids.)
