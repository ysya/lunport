# AI edits hosts and transports with consent: implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Three MCP tools (`update_host`, `set_transport`, `remove_transport`) that propose a change to a permitted host's connection settings or its Google Cloud IAP transport, show it in Lunport's approval window as `old → new` rows, and save only on the person's click.

**Architecture:** The tools live beside `create_host` in `src-tauri/src/mcp/management.rs` and follow its shape exactly: parse input → build a candidate state and its proposal rows on a snapshot → `wait_approval` through the existing window → rebuild the candidate inside `edit_records`, refuse if the rows changed, save → audit. `McpHostProposal` gains a `kind`, which the window uses for its title, description and button. `metadata` (the sanitized host view) gains the host's transport so the client can see what it edits.

**Tech Stack:** Rust (Tauri 2, serde, ts-rs), React/TypeScript (vitest static markup), the existing MCP runtime (`McpRuntime::wait_approval`, 120 s), the records repository (`record_repository::update_host` with `RecordRevision`), `sync::transports` (`get`, `set` with `expected`, `HostTransport::validate`).

**Spec:** `docs/superpowers/specs/2026-10-26-mcp-edit-hosts-transports-design.md`

## Global Constraints

- Every tool asks through the window in Ask and Auto-log mode alike, with the window's 120-second expiry; the client never approves.
- Secrets never enter a proposal, the window, an audit entry or an error: a `key_id` shows as the key's name and fingerprint (as `candidate` does), never material; `host_key`, passwords and private keys are not accepted as input (`deny_unknown_fields`).
- Only hosts the client may use (`permissions::ensure_record`) can be edited; the refusal sentences are `get_host`'s own (`repo::get_host(...).or_else(find_by_alias)` errors, then `host '<id>' is not allowed for AI access`).
- Validation and its sentences are the editor's: `record_repository::update_host` for hosts, `HostTransport::validate` for transports.
- `group_id` is not accepted by `update_host`; `host_key` is never set by the tools (the repository clears it when the effective address changes).
- Rows are `(label, value)`; a changed field's value is `"<old> → <new>"`; a field the host inherited from its Group shows the old value as `"<value> (from Group <name>)"`.
- Conflict sentences: `The host changed while the request was open; read it again and retry.` and `The transport changed while the request was open; read it again and retry.`; a proposal without a change: `Nothing would change.`
- Commits are conventional; bindings regenerated by Rust tests are kept only for `McpHostProposal.ts` (strip trailing whitespace; revert the rest with `git checkout -- src/bindings/`).

## Review Focus

1. A client sends a field whose value equals the current effective value (or the same transport): the tool answers `Nothing would change.` before any window (Task 3 and Task 4 tests).
2. A host whose Group inheritance is broken (`group_error`): `update_host` refuses as `metadata` does (`Host Group inheritance needs review.`), never saving over it (Task 3 test).
3. A `jump` that names the host itself or loops: the repository's `validate_host` sentence comes back, nothing is saved, no window (Task 3 test).
4. The window's rows carry untrusted text (an alias with `<script>`): the frontend escapes it through `revealHidden` as it does today (Task 1 test).
5. The approval is denied, cancelled or times out: the host and its transport are exactly as before, the audit entry says so (Task 3 and Task 4 tests).
