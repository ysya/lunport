The public `macos-project.pem` pins Lunport's macOS code-signing identity. Stable and Beta use this same certificate and the production bundle identifier `dev.ysya.lunport`. Its SHA-256 fingerprint is:

```
fb598161e18d2e34dced4a418fbcd478ffdbfa5dd395095c5da0b59826ed986c
```

Code requirements name the certificate by its SHA-1, `66f062921154fb6fe72e7ee0dfe99d7d804efb03` (`certificate leaf = H"…"`). `legacy/macos-project.pem` is the certificate releases before 2.0.0 were signed with; helper v1 and the bridge to it stay signed with that one, and their verifiers pin it.

This self-signed project certificate preserves the designated requirement across rebuilds. Keychain also has a separate partition check: self-signed code receives a per-build `cdhash` partition rather than an Apple-verified Team ID. Existing items restricted to an earlier hash can request authorization again despite a stable designated requirement and Always Allow. The certificate is not an Apple Developer ID and does not provide notarization or Gatekeeper approval. Never rotate it per release or replace it with ad-hoc signing. Changing the certificate requires a deliberate migration and can require user authorization again.

The encrypted PKCS#12 identity and password are stored in repository secrets `LUNPORT_MACOS_CERTIFICATE` (base64) and `LUNPORT_MACOS_CERTIFICATE_PASSWORD`. The owner keeps the recovery copy outside the repository with owner-only permissions. Treat both files as private signing material and back them up securely; they must never enter Git, artifacts or logs. Only public certificate and signed executable data belong in source control.

`scripts/macos-signing.sh` imports the identity into a temporary CI keychain, checks it against `macos-project.pem` (the pin is this file, so the secrets and the file change together), and restores the search list on cleanup. It never installs a trusted root. `scripts/build-macos-release.sh` checks both universal architectures, the embedded certificate and the designated requirement in the App and updater archive before tauri-action uploads assets. Missing or changed credentials fail the build instead of silently reverting to unsigned output.

`scripts/validate-macos-keychain.sh` checks both an unrestricted fixture in a newly created legacy keychain and a modern `SecItemAdd` fixture in the disposable runner's existing login keychain. The modern fixture must have a partition ACL and reject a different executable build even when its certificate and designated requirement match. A different signer is denied too. All fixtures use disposable CI credentials and are removed during cleanup.

The user-approved fixed helpers address the per-build partition gate: each is a signed universal artifact embedded as data and installed outside the replaceable App bundle, and its public manifest records artifact/source hashes and architecture code hashes. Never rebuild or re-sign one during ordinary releases. Helper v2 (`credential-helper-v2.c`, identifier `dev.ysya.lunport.credential-helper.v2`, signed with `macos-project.pem`) keeps Production credentials under the service `Lunport`. Its `credential-helper-v2.bin` (SHA-256 `1b4ba95a61d4ebe80037beaae22a5c2d355cad6dfcfa2d67d22cce510822c774`) and manifest are committed here from a reviewed candidate of the `freeze_helper` dispatch of the macOS credentials workflow, and `src-tauri/src/identity.rs` pins their values; a Production build does not compile while those are placeholders. Helper v1 (`legacy/credential-helper-v1.*`), which releases before 2.0.0 used, stays only for the credential migration, which reaches it through the bridge. `verify-macos-credential-helper.py --version v1|v2` rejects changed bytes or source, a certificate other than the one that version is pinned to, a wrong identifier, a missing architecture, a signature without hardened runtime and any entitlement. `build-macos-credential-helper.sh` is an explicit candidate-generation workflow only; a new helper version requires a migration/review and can need authorization again.

`validate-macos-helper.sh` checks helper-owned modern partitions, two different client builds, pre/post-approval legacy fixtures, rejected clients, forged helpers and malformed requests. `validate-macos-bridge.sh` builds the bridge, helper v1 and helper v2 from source with disposable certificates and checks the bridge-to-helper-v1 chain and its refusals and helper v2 with its adopt operation in a disposable keychain; on a CI runner it also checks which program owns the items helper v2 saves, in the runner's login keychain. The OS authorization dialog itself is a manual check. `validate-macos-frozen-helper.sh v1|v2` checks an exact frozen artifact with two production-signed clients; with the current certificate only helper v2 can pass, since helper v1 accepts only a parent signed with the previous one. `validate-macos-helper-rust.sh` signs a CI-only test executable as the app and checks the actual Rust channel and installation/recovery against helper v2 with public disposable credentials. Only `validate-macos-bridge.sh` may run outside a disposable CI runner: there it works only in its own temporary keychain under a temporary HOME. None may run on a user's Keychain. Production never changes an item's ACL or partition list.
