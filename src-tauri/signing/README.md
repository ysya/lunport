The public `macos-project.pem` pins Lunport's macOS code-signing identity. Stable and Beta use this same certificate and the production bundle identifier `org.homelab.sshelter`. Its SHA-256 fingerprint is:

```
6bce9f14c85274ab36911c91c48e52249e49089afee80e6465b54ab6f4174830
```

This self-signed project certificate preserves the designated requirement across rebuilds. Keychain also has a separate partition check: self-signed code receives a per-build `cdhash` partition rather than an Apple-verified Team ID. Existing items restricted to an earlier hash can request authorization again despite a stable designated requirement and Always Allow. See the [follow-up](../../docs/2026-10-18-keychain-partition-followup.md). The certificate is not an Apple Developer ID and does not provide notarization or Gatekeeper approval. Never rotate it per release or replace it with ad-hoc signing. Changing the certificate requires a deliberate migration and can require user authorization again.

The encrypted PKCS#12 identity and password are stored in repository secrets `LUNPORT_MACOS_CERTIFICATE` (base64) and `LUNPORT_MACOS_CERTIFICATE_PASSWORD`. The initial local recovery copy is in the ignored `.local-signing/` directory with owner-only permissions. Treat both files as private signing material and back them up securely; they must never enter Git, artifacts or logs. Only public certificate and signed executable data belong in source control.

`scripts/macos-signing.sh` imports the identity into a temporary CI keychain, checks the certificate pin, and restores the search list on cleanup. It never installs a trusted root. `scripts/build-macos-release.sh` checks both universal architectures, the embedded certificate and the designated requirement in the App and updater archive before tauri-action uploads assets. Missing or changed credentials fail the build instead of silently reverting to unsigned output.

`scripts/validate-macos-keychain.sh` checks both an unrestricted fixture in a newly created legacy keychain and a modern `SecItemAdd` fixture in the disposable runner's existing login keychain. The modern fixture must have a partition ACL and reject a different executable build even when its certificate and designated requirement match. A different signer is denied too. With `--with-rust`, the production metadata query must find an item without gaining access to its protected password. All fixtures use disposable CI credentials and are removed during cleanup.

The user-approved fixed helper addresses the per-build partition gate: `credential-helper-v1.bin` is a signed universal artifact embedded as data and retained outside the replaceable App bundle. Its public manifest records artifact/source hashes and architecture code hashes. Never rebuild or re-sign it during ordinary releases. `verify-macos-credential-helper.py` rejects changed bytes/source, wrong certificates, wrong identifiers, missing architectures or runtime hardening. `build-macos-credential-helper.sh` is an explicit candidate-generation workflow only; a new helper version requires a migration/review and can need authorization again.

`validate-macos-helper.sh` checks helper-owned modern partitions, two different client builds, pre/post-approval legacy fixtures, rejected clients, forged helpers and malformed requests. The OS authorization dialog itself is a manual check. `validate-macos-frozen-helper.sh` checks the exact production artifact with two production-signed clients. `validate-macos-helper-rust.sh` signs a CI-only test executable and checks the actual Rust channel and installation/recovery with public disposable credentials. Neither script may run on a user's Keychain. Production never changes an item's ACL or partition list.
